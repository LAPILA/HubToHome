## 3차 확인: UI 정책과 Canvas A 첫 적용

- `docs/plans/2026-08-30-ui-viewport-policy-and-overworld.md`에 단계별 구현 계획을 기록했다.
- TestMap 런타임에는 별도 UI Camera가 없고 `PPC` Game Camera만 존재하는 것을 Unity MCP로 확인했다. 첫 단계에서는 중복 카메라를 만들지 않고 Game Camera를 FixedViewport Canvas의 공통 출력 카메라로 재사용한다.
- `UIViewportService`와 `UIViewportServiceTests`를 추가하고, UIManager가 Overworld 패널을 FixedViewport로 등록하도록 연결했다. 내부 인벤토리/메뉴 계층과 직렬화 참조는 변경하지 않았다.
- `UIViewportServiceTests.ConfigureFixedViewportUsesSharedCameraAndNeverExpand` EditMode 테스트 1개가 통과했다.
- 변경 후 Windows 개발 빌드 `Builds/Windows/HubToHome.exe`가 성공했고 실행 중이다. 현재 캡처는 Battle 상태여서 Canvas A 오버월드 메뉴/인벤토리의 실제 화면 검증은 아직 완료하지 못했다.
- Unity 자동 생성/갱신으로 표시된 RenderSettings, TMP 리소스, ProjectSettings 변경은 이번 UI 코드 변경과 별개로 남아 있으며, 커밋 전에 내용과 원인을 재검토해야 한다.

## 6차 확인: 아이템 획득 대화와 상점 UI의 공통 등록 누락

- QA 아이템 상호작용 메시지는 별도 대화창이 아니라 `ItemPickupMarker`가 `AreaMarkerRuntimeService`와 `DialogueManager`를 통해 `DialogueCanvas/OverworldPanel`을 사용하는 경로로 확인했다.
- 첫 전체화면 진입 직후 대화가 늘어나는 경우를 보완하기 위해 `DialogueUI.OpenPanel()`에서 표시 직전에 `UIViewportService` 등록을 다시 수행하도록 했다. 비활성 UI의 `Awake()` 시점과 화면 전환 시점이 어긋나도 FixedViewport 설정이 적용된다.
- `ShopUI`는 `BuildView()`에서 런타임 Canvas를 새로 만들고 `ScreenSpaceOverlay`로만 설정하고 있어 게임 카메라의 4:3 viewport를 우회했다. 생성 직후 공통 FixedViewport 서비스에 등록하도록 했다.
- 두 UI 모두 기존 계층/입력/거래·대화 로직은 유지하고 Canvas 출력 정책만 공통 경로로 통합했다.
- 후속 검토에서 UI별 직접 서비스 호출은 정책 중복으로 판단했다. `UIRuntimeGuard.NormalizeCanvas()`가 Canvas 보정과 `UIViewportService` 등록을 함께 담당하도록 정리해 Dialogue, Shop, 설정, 전투 UI가 같은 공통 진입점을 사용하게 했다.

## 7차 확인: 전체화면 직후 인벤토리 탭 레이아웃 안정화

- 인벤토리 탭의 개별 RectTransform은 수정하지 않았다. 증상은 전체화면 직후 카메라 rect, CanvasScaler, SafeArea, LayoutGroup이 서로 다른 프레임에 갱신되는 초기화 순서 문제로 판단했다.
- `UIViewportService`에 화면 변경 후 두 프레임과 EndOfFrame을 기다리는 공통 안정화 루틴을 추가했다.
- 안정화 시점에 등록된 FixedViewport Canvas, `UIPixelPerfectSafeAreaFitter`, `LayoutRebuilder`를 순서대로 재적용해 첫 전체화면 표시에서도 탭 부모 영역과 자식 배치를 함께 재계산한다.
- 관련 EditMode 테스트 9/9 통과 및 컴파일 오류 0개를 확인했다. Windows 빌드 후 첫 전체화면에서 인벤토리 탭을 다시 육안 확인해야 한다.
