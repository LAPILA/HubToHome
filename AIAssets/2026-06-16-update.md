## [의도]

- QTE 모듈화가 끝난 뒤 다음 위험은 “새 모듈을 추가해도 결국 QTE UI와 입력이 남아 있는가”였습니다.
- 이번 변경은 아직 완성된 슈팅 게임을 만드는 단계가 아니라, 비-QTE 모듈이 전투 Primary Mode 안에서 QTE와 같은 Game Module Runner를 타고 들어오며 자기 UI/입력 소유권을 잡을 수 있는지 확인하는 단계입니다.
- `aim_shooter`를 registry에 넣어둠으로써 Battle Scenario Data의 `module.switch: aim_shooter` / `module.start: aim_shooter`가 hard-coded BattleManager 분기 없이 동작할 토대를 만들었습니다.
- `IBattleAimShooterModuleController`는 다음 단계의 실제 shooter gameplay loop가 들어갈 자리입니다. 이 seam이 없으면 mouse aim, projectile, damage, outcome 보고가 다시 BattleManager 또는 UI controller에 섞일 위험이 큽니다.
- `BattleAimShooterCombatSession`은 그 controller 뒤에서 호출될 순수 규칙 Module입니다. 이 코어가 있으면 input/projectile/VFX 구현은 presentation/input adapter에 머물고, 데미지와 outcome policy는 테스트 가능한 곳에 남습니다.

## [위험 / 후속]

- `aim_shooter`는 아직 완성 모듈이 아닙니다. 다만 이번 더미 vertical slice로 실제 shooter 구현 없이도 모듈 전환/시작/outcome/follow-up sequence 통로는 코드상 검증했습니다.
  - 남은 것: 조준 입력, 타겟/탄환/피격 판정, UI, 카메라/배경 presentation, `IBattleParticipantCommandRunner` damage 요청, `IGameModuleEventSink` outcome 보고.
- 다음 구현자는 `aim_shooter` gameplay를 `IBattleAimShooterModuleController` 뒤에 붙이고, mouse input/projectile hit 결과를 `BattleAimShooterCombatSession.FireAt(...)`으로 전달해야 합니다.
- 실제 적 HP 스냅샷은 현재 read-only snapshot이므로, shot 후 UI/스냅샷 갱신 타이밍은 기존 `IBattleParticipantCommandRunner` adapter와 BattleManager event bridge 검증이 필요합니다.
- 실제 Unity Editor Play/EditMode validation은 MCP 연결이 다시 잡힌 뒤 필요합니다.
- 비-QTE 모듈이 늘어날수록 `IBattleGameModulePresentationController`가 임시 UI adapter에서 더 정식 Presentation Service로 깊어질 가능성이 큽니다.
- `ScenarioSourceYamlParser`는 현재 범용 YAML parser가 아니라 writer-supported subset parser입니다. anchors, multiline scalar, 임의 중첩 map을 쓰는 source는 아직 지원하지 않습니다.
- `ScenarioAuthoringWindow`의 action 조작은 runtime asset의 sequence list를 가볍게 편집하는 단계입니다. 안전한 runtime asset reimport/replace는 남아 있습니다.

- `ScenarioSourceRuntimeAssetReimportCommand`를 추가했습니다.
  - `BattleScenarioData.Source.SourcePath`의 YAML을 읽어 임시 `BattleScenarioData`로 import합니다.
  - parser/import/catalog validation이 성공한 뒤에만 기존 target `BattleScenarioData`를 갱신합니다.

  - 기존 sequence는 `SequenceId` 기준으로 재사용해서 에셋 참조 안정성을 유지합니다.
  - 새 sequence는 target이 persisted asset이면 sub-asset으로 추가하고, 더 이상 source에 없는 sequence는 목록에서만 분리합니다.
  - 기존 sequence asset을 자동 삭제하지 않습니다. 사람이 만든 참조가 남아 있을 수 있기 때문입니다.
- `ScenarioAuthoringWindow`에 `런타임 에셋 반영` 버튼을 추가했습니다.
  - source path가 있는 `BattleScenarioData`에서만 활성화됩니다.
  - 성공 시 재사용/생성/분리된 sequence 수를 표시하고 화면을 갱신합니다.
  - 실패 시 validation 메시지를 보여주고 runtime asset은 보존합니다.
- `ScenarioSourceYamlParser`가 YAML의 `parallel:` 축약 문법을 runtime action ID `flow.parallel`로 정규화하도록 수정했습니다.

  - Unity coroutine runner와 pure EditMode test runner의 실행 차이 때문에 후속 module-completed sequence가 테스트에서 끝까지 실행되지 않던 문제를 해결했습니다.

## [추가 위험 / 후속]

- 실제 production scenario asset에 대한 수동 reimport 검증은 아직 하지 않았습니다. 현재 검증은 editor command 단위와 EditMode test 중심입니다.
- `ScenarioActionData.Children`는 recursive 구조라 sequence 전체를 Unity Undo에 기록하면 `Serialization depth limit 10 exceeded`가 발생했습니다. 그래서 reimport command는 target scenario에는 Undo를 기록하지만, sequence action list 자체는 dirty marking으로 처리합니다.
- 이 기능은 runtime asset을 안전하게 갱신하는 단계입니다. 다음 큰 단계는 실제 ZEV phase-transition source/asset vertical slice입니다.
