ScriptID를 class114에서만 읽은 첫 시도는 다른 script-index 타입에서 타입 테이블 위치가 어긋났음. `scriptTypeIndex >= 0`일 때 16바이트를 소비한 뒤 성공. metadata 시작48, type-tree node32바이트, big-endian header dataOffset, object별 int64 ID/offset을 확인. 64비트 ID는 JavaScript Number로 변환하지 않음. 적용 조건은 이 엔진 산출물 v22이며 다른 버전에 일반화하지 않음. 검증은 5개 clip 이름과 5개 sprite 이름 및 원본 step 태그를 대조. 관련: WizelPressure.asset, BattleResourceTests.

## 재사용 가능한 하네스 교훈

1. **원본 파싱 성공만으로 내용 보존을 판단하지 않기.** parallel 들여쓰기 불일치가 오류 없이 빈 자식을 만들었음. 빌드된 C# 파서를 관리 어셈블리로 로드해 순수 DTO만 생성하면 Unity Play 없이 재현 가능. 네이티브 ScriptableObject 생성은 이 경로에서 하지 않음. 검증은 중첩 액션 수·순서·ID·파라미터를 함께 비교. 관련: `ScenarioSourceExporter.cs`, `BunnySlimeLabStoryTests`.
2. **Windows 메타데이터 줄 끝.** `rg '^guid: [0-9a-f]{32}$'`는 CRLF 파일을 빠뜨려 기존 GUID가 없다는 오탐을 냈음. `$`를 제거하거나 `\r?$`로 읽고 실제 `.meta` 존재를 확인하면 통과. 파일 손상으로 단정하거나 재생성하지 않음.
3. **구조화된 도구 출력 제한.** 큰 변경 파일 전체를 JSON으로 받으면 출력이 잘려 파싱 실패할 수 있고 Git의 CRLF 경고도 JSON 앞에 섞일 수 있음. 필요한 실험실 자산으로 범위를 줄이고 Git 경고 스트림을 분리한 뒤 파싱. 한 번 실패한 대형 조회를 그대로 반복하지 않음.

전역 yjlim 메모리 경로가 없는 현재 taehw 환경에서는 위 교훈을 이 프로젝트 기록에 남깁니다. 인증/그룹 조회는 수행하지 않았습니다.
