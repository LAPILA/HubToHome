## [분석 결론]

- 기존 전투/대화/UI/스킬 시스템을 즉시 갈아엎는 방식은 권장하지 않습니다.
- 새 `ActionDirector` / `ActionSequence` 계층을 먼저 만들고, 기존 시스템은 Adapter로 감싸서 현재처럼 동작하게 만드는 방향이 적합합니다.
- 이후 새 연출, 전투 모듈, 미니게임, 시네마틱 전환은 새 계층 위에서 작성하는 방식이 안전합니다.
- HP 임계치, 첫 조우/재조우, 모듈 전환 같은 전투 중 사건은 개별 스킬 타임라인이 아니라 전투/적 데이터에 작성된 `Battle Event Rule`로 관리하는 방향이 적합합니다.
- `TurnQTECombatModule`, 슈팅, 권투 같은 전투 Game Module은 `Battle Session State`를 공유하고, 모듈 전환 연출은 `Action Director`가 실행하는 방향으로 정리했습니다.
- `Battle Event Rule`은 주로 `EncounterDefinition` / `BattleScenarioData`가 소유하고, `EnemyData`는 적 자체의 기본 능력치, 스킬, 프리팹, 기본 성향을 유지하는 쪽이 적합합니다.
- `Encounter Memory`는 델타룬/언더테일식 세이브 포인트 구조에 맞춰 저장/로드 대상 상태로 다뤄야 합니다.
- 저장/로드 경계는 전투 밖으로 둡니다. 전투 진행 중인 `Battle Session State`는 저장 복구 대상이 아니며, 전투 결과와 조우 이력만 `Encounter Memory`/저장 데이터로 반영하는 방향입니다.
- 액션 종류가 많아지는 것은 허용하되, 사람은 "이 전투는 어떤 흐름이고 어떤 이벤트가 있다"를 서술하고 AI가 그에 맞는 규칙과 Action Sequence를 작성하는 작업 모델을 전제로 합니다.
- 시나리오 저작은 `YAML Scenario Source -> validation/import -> ScriptableObject Scenario Runtime Asset -> Korean Scenario Authoring Editor`의 하이브리드 구조를 기준으로 합니다.
- AI는 주로 Scenario Source와 Action Catalog를 수정하고, 사람은 커스텀 에디터에서 읽기/순서변경/삽입/가벼운 필드 수정을 하는 모델이 적합합니다.
- 시나리오 파이프라인이 바뀔 때는 코드나 문서만 바꾸지 않고 `.agents/skills/hubtohome-scenario-authoring/`도 함께 최신화해야 합니다.

## [검증]

- 코드/씬/프리팹/에셋은 수정하지 않았습니다.
- Unity Editor PlayMode, 씬 저장, asset reimport는 수행하지 않았습니다.
- 분석은 `rg`, PowerShell 파일 스캔, 기존 `AIAssets`/`docs` 문서, 주요 C# 파일 정적 확인 기준으로 진행했습니다.
- `.agents/skills/hubtohome-scenario-authoring`는 `skill-creator` 템플릿으로 생성한 뒤 프로젝트 규칙으로 작성했고, `quick_validate.py` 검증을 통과했습니다.
- `specify init --here --ai codex --ai-skills --script ps` 초기화는 현재 환경에서 실패했습니다. `--offline`은 `pwsh` 미설치로 실패했고, 온라인 시도는 `spec-kit-template-codex-ps` 릴리스 자산을 찾지 못했습니다. 따라서 이번에는 최소 Spec Kit 문서를 수동 작성했습니다.
