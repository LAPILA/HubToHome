Action Director 도입 전 기존 시스템 해부와 이관 지도

목표는 Deltarune식 Overworld/Battle 전환, 전투 중 모듈 교체, 미니게임, 대화, 시네마틱, UI 전환을 한 실행 문법으로 다룰 수 있는 기반을 세우는 것이다. 결론은 기존 전투를 즉시 갈아엎지 않고, 새 Action/Sequence 계층을 위에 얹은 뒤 기존 시스템을 Adapter로 감싸 점진 이관하는 쪽이다.

Top Decision
새 구조를 먼저 만들고, 기존 전투/대화/UI/스킬 시스템은 Adapter로 감싸서 현재처럼 동작하게 만든다. 이후 새 연출과 새 Game Module은 Action Director 위에서만 작성한다.
Keep

유지할 것

이미 역할이 선명하거나 데이터 자산 가치가 큰 모듈.

  • BattleEncounterService
  • SceneLoader, MapTransitionService
  • DialogueData, DialogueManager의 출력 기능
  • UIManager, UIPanel의 패널 스택
  • SkillData와 현재 스킬 에셋
  • CharacterBase, PlayerCharacter, EnemyCharacter
Adapter

감싸서 쓸 것

현재 동작은 살리되, 새 계층이 직접 의존하지 않도록 감쌀 모듈.

  • BattleManager → Legacy Battle Primary Adapter
  • SkillActionBlock → Legacy Skill Timeline Action
  • QTEManager → QTE Presentation/Rule Adapter
  • BattleUIController → Battle UI Registry Adapter
  • PlayerController → Actor Motor Adapter
  • CameraController → Camera Presentation Adapter
New

2. 목표 구조 지도

핵심 원칙

  • Primary Mode는 Overworld/Battle 두 개만 둔다.
  • QTE, Shooter, Boxing, 미니게임은 Game Module로 취급한다.
  • 대사, UI, 카메라, 사운드, VFX는 모듈 소유가 아니라 Presentation Service다.
  • 연출 흐름은 ActionDirector가 실행한다.
  • 기존 시스템은 한 번에 삭제하지 않고 Adapter로 연결한다.

한 줄 구조

Overworld / Battle → GameModuleRunner ↔ ActionDirector → Presentation Services → Legacy Adapters

3. 기존 시스템별 판단표

영역 현재 상태 판단 이관 방식 주의점
BattleManager 1435줄. 상태 전이, 유닛 생성, 턴, 플레이어 행동, 적 행동, QTE, 스킬, 종료/복귀까지 집중. Adapter 후 단계 분리 처음에는 LegacyBattlePrimaryAdapter로 감싼다. 새 모듈이 검증된 뒤 행동 실행/방어 판정/종료 처리부터 빼낸다. 가장 위험한 파일. 첫 단계에서 직접 분해하면 회귀 위험이 크다.
SkillActionBlock 이미 데이터 기반 액션 목록이 있다. 하지만 SkillContext가 전투 캐릭터와 BattleManager.Instance에 묶여 있다. 유지 + Adapter RunLegacySkillTimelineAction으로 실행 가능하게 감싼다. 새 액션 시스템의 설계 참고자료로 쓴다. 전역 Action의 부모 클래스로 승격하지 않는다.
BattleEncounterService 오버월드/대화/지역 트리거에서 전투 진입을 공통 처리한다. 유지 나중에 BattlePrimary.Enter 또는 EncounterAction에서 호출한다. 현재 구조에서 제일 좋은 진입 seam 중 하나다.
DialogueManager 대사 출력, 선택지, 이름 입력, 선택지 전투 시작까지 처리한다. Adapter DialogueService.ShowAndWait가 내부에서 기존 StartDialogue를 감싼다. 대사는 Game Module 소유가 아니다. 어디서든 호출 가능해야 한다.
UIManager/UIPanel 패널 등록, 패널 스택, 취소 입력 처리, PPC safe area 지원. 유지 + 확장 UIRegistry를 추가하고 panel ID를 안정화한다. Action은 ID로 UI를 제어한다. 전투 UI는 별도 Adapter가 필요하다.
QTEManager 방어 QTE와 스킬 QTE를 실행하고 BattleUI를 직접 호출한다. Adapter QteAction, DefenseWindowAction에서 호출. 이후 규칙과 UI 표현을 분리한다. Shooter/Boxing 같은 새 모듈은 QTEManager를 통하지 않아야 한다.
PlayerController 오버월드 이동, 전투 모드, 방어 입력/연출, Y정렬, 저장 위치까지 담당. Adapter 후 역할 분리 ActorMotorAdapter가 이동/넛지/방어 연출을 호출한다. 입력 소유권은 나중에 Input Router로 이동한다. Town 액션과 Battle 액션이 모두 플레이어를 움직일 수 있어 registry가 필요하다.
MapTransitionService Scene/Room 전환을 통합한다. RoomDefinition 기반 제작 흐름이 있다. 유지 ChangeRoomAction, ChangeSceneAction으로 감싼다. 씬 합치기 여부와 독립적으로 Action Sequence와 잘 맞는다.
GlobalDataManager 파티/월드/조우/저장 복구 데이터를 한 곳에 둔다. 유지하되 세분화 후보 초기에는 SessionState 제공자. 나중에 BattleSessionState, WorldSessionState로 나눈다. 전투 중 모듈이 바뀌어도 HP/MP/status는 여기에 가까운 상태 계층이 보존해야 한다.

4. Action 문법 설계

Action 카테고리

  • Actor: 이동, 넛지, 애니메이션, 포즈, sorting boost
  • Dialogue: 대사 시작, 선택지 대기, 이름 입력
  • UI: 표시, 숨김, fade, layout preset, panel stack
  • Camera: follow, zoom, shake, target blend
  • Audio/VFX: BGM, SFX, VFX spawn/despawn
  • Flow: wait, branch, parallel, cancel, flag
  • Module: enter, exit, switch, handoff input
  • Legacy: old skill, old QTE, old battle routine

병렬 실행 문법

병렬은 액션 하나의 옵션이 아니라 Sequence의 1급 문법이어야 한다.

ParallelGroup
  • WaitAll: 전부 끝날 때까지 대기
  • WaitAny: 하나만 끝나도 다음으로 진행
  • FireAndForget: 시작만 하고 다음으로 진행
  • Timeout: n초 후 강제 진행/취소

클래스 수에 대한 판단

액션은 필요할 때마다 새 클래스를 만들어도 된다. 대신 공통으로 반복되는 선택/타겟/시간/취소/카테고리 메타데이터는 공유한다.

  • MoveActorAction은 공통화
  • DrawSwordAction은 전용 액션 가능
  • BattleHudToShooterLayoutAction도 전용 액션 가능
  • 제작자 사용성이 추상화 순도보다 우선

5. Target / UI / Actor 바인딩

ActorRegistry

액션이 GameObject를 직접 들고 다니지 않도록, 런타임 Actor ID를 해석한다.

  • Player(0), Player(1)
  • MainEnemy, EnemyById("zev")
  • NamedActor("npc_blacksmith")
  • CurrentSpeaker, CurrentTarget

TargetResolver

위치도 ID로 찾는다. Battle과 Town에서 같은 액션을 쓰려면 이 계층이 필요하다.

  • Marker("Center")
  • ActorPivot(target, "Front")
  • BattleSlot.Enemy(0)
  • RoomSpawn("door_left")

UIRegistry

UI는 안정 ID로 제어한다. 씬 오브젝트 이름 검색은 Adapter 내부로 숨긴다.

  • Battle.HUD.Root
  • Battle.HUD.QTE
  • Battle.HUD.Shooter
  • Dialogue.Main
  • Overworld.Menu
  • Overworld.InteractionPrompt

7. 마이그레이션 순서

용어와 seam 고정

CONTEXT.md에 Primary Mode, Game Module, Action Sequence, Action Director, Presentation Service를 고정한다. 이 단계는 코드 변경보다 중요하다.

ActionDirector 최소 런타임 추가

처음에는 Wait, Log, Parallel, Cancel 정도만 된다. 목표는 행동 완성이 아니라 실행 모델 검증이다.

Legacy Adapter 작성

ShowDialogueAction, RunLegacySkillTimelineAction, RunLegacyDefenseQteAction, UIShowHideAction으로 기존 시스템을 새 Sequence에서 호출하게 만든다.

첫 실제 전환 Sequence 제작

새 전투 모듈을 크게 만들기 전에 QTE UI 숨김, 대사, 캐릭터 이동, 카메라, UI 복귀 같은 순수 전환 시퀀스를 하나 만든다.

GameModuleRunner 도입

처음에는 LegacyQteCombatModule 하나만 등록해도 된다. 그 다음 AimShooterPrototypeModule을 붙여 모듈 교체를 검증한다.

BattleManager 분리 시작

새 실행 계층이 실제로 돌아간 뒤, EnemyActionRoutine, 방어 판정, 종료 처리를 순서대로 BattleManager 밖으로 빼낸다.

8. 추천 우선순위

Strong

ActionDirector + SequenceRunner 최소판

가장 먼저 해야 한다. 이게 있어야 기존 시스템을 감싸는 방향이 맞는지 검증할 수 있다.

Strong

Registry 3종

ActorRegistry, UIRegistry, TargetResolver가 없으면 액션이 씬 오브젝트 참조와 문자열 검색으로 무너진다.

Worth Exploring

Odin/SerializeReference 기반 리스트 에디터부터 시작하고, 노드 그래프는 나중에 제작량이 실제로 많아질 때 판단한다.

10. 최종 권고

기존 시스템을 새 구조로 먼저 리팩터링하지 말고, 새 구조를 별도 계층으로 만든 뒤 기존 시스템을 어댑터로 연결하는 Strangler 방식이 맞다.

현재 프로젝트는 이미 플레이 가능한 수직 슬라이스가 있고, 전투/대화/조우/저장/룸 전환의 재료가 존재한다. 이 재료를 버리면 손실이 크다. 하지만 기존 BattleManager를 중심으로 확장하면 Shooter, Boxing, Town 미니게임, 시네마틱 전환까지 전투 중심 구조에 갇힌다.

따라서 첫 공사는 ActionDirector, ActionSequenceAsset, ActionExecutionContext, ActorRegistry, UIRegistry, GameModuleRunner의 최소판이다. 이 위에서 기존 전투를 그대로 한 번 돌려보고, 그 다음 새 전환 시퀀스와 새 모듈을 붙이는 순서가 가장 안전하다.

작성 범위: 정적 소스 분석 기준. Unity 씬 저장, PlayMode, asset reimport는 수행하지 않음.
