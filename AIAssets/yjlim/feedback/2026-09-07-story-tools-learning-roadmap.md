# 대사·스토리 제작 도구 정리와 학습·포트폴리오 방향

작성일: 2026-09-07 · 브랜치: `codex/gameplayEdit`

현재 코드와 앞선 논의를 정리한 다음 작업 기준이다. 이 문서 작성으로 아래의 미구현 기능이 구현된 것은 아니다. 코드·씬·프리팹 변경, 테스트 실행, 커밋/푸시는 하지 않았다.

후속 구현: 대사 메이커의 작업 화면·기존 조건 문서 편집/NPC 연결·빈 본문 키 생성은 이후 작업에서 추가했다. 현재 사용법은 [콘텐츠 메이커 가이드](../../../docs/content-maker-guide.md), 학습 내용은 [프로젝트 학습 목차](../../../docs/learning/README.md)를 기준으로 한다. 아래의 NPC 위치·출현/범용 사건·선택 결과/전체 번역 확장까지 완료한 것은 아니다.

## 1. 목표와 범위

플레이어의 행동에 따라 NPC의 대사·출현과 사건이 달라지는 게임을 만든다. 동시에 제작 흐름을 직접 이해하고 수정할 수 있는 학습 프로젝트로 사용한다.

NPC마다 모든 진행 코드를 작성하면 수정 지점이 흩어진다. 모든 잡담까지 시퀀스로 작성하면 간단한 대본 편집도 복잡해진다. 기존 실행 시스템을 유지하면서 상태, NPC 반응, 사건, 대본의 역할을 나누는 방식을 선택한다. 범용 엔진이나 새 노드 편집기를 추가하는 것은 이번 목표가 아니다.

| 구분 | 책임 | 관리 원칙 |
| --- | --- | --- |
| 이야기 상태 | 플레이어가 확정한 사실, 메인 진행 단계, 완료 사건 | 저장 상태는 기존 GlobalDataManager를 기준으로 한다. 임시 전투 상태와 분리한다. |
| NPC 상태 | 조건별 등장 장소·표시 여부·대화 | 후보 상태 중 우선순위로 하나를 고르고 기본 반응을 둔다. |
| 대화 | 화자·표정·문장·선택지 | NPC와 시퀀스가 같은 대화 데이터를 참조한다. 프리팹 안에 긴 대본을 복제하지 않는다. |
| 스토리 사건 | 시작 계기·조건·실행 시퀀스·완료 결과 | 챕터 하나를 사건 목록으로 나눈다. |
| 시퀀스 | 이동·대화 대기·공격·카메라 등 사건의 실행 순서 | 기존 시퀀스 메이커와 Action Director를 재사용한다. |
| 번역 | 고정 문장 ID에 대응하는 언어별 문구 | 본문·선택지·화자 이름을 포함한다. 문장 순서나 파일명 변경으로 ID를 재발급하지 않는다. |

## 2. 현재 구현과 추가 작업을 구분한다

| 영역 | 현재 확인한 것 | 앞으로 보완할 것 |
| --- | --- | --- |
| 진행 상태 | GlobalDataManager의 정수 플래그와 변경 알림, 저장·로드 | 기획자가 읽을 상태 이름/설명/허용 값과 사용 위치 관리 |
| 일반 NPC 대화 | FlagDialogueSelector의 단일 플래그 비교, 우선순위, 기본 대본 | 복수 조건과 상태별 대본을 메이커에서 한 목록으로 편집 |
| NPC 출현 | FlagStateBinder로 지정 오브젝트/렌더러 표시·숨김 | 논리적 NPC의 후보 장소와 등장 조건을 함께 관리. 현재 기능을 자동 이동 시스템으로 소개하지 않는다. |
| 선택지 | 다음 대화, 플래그를 1로 설정, 전투 시작 | 안정적인 선택 결과 ID와 완료/취소 결과를 시퀀스에 전달 |
| 사건 실행 | 씬 진입/상호작용 시퀀스, 성공 후 일회 완료 기록 | 방 진입·조사·선택·전투 결과를 조건과 연결하는 오버월드 사건 규칙 |
| 번역 | 대사 본문 LocalizationKey와 기본 문구, Resources 번역 표 | 선택지·이름 번역, 키 발급/검사, 번역 추출/가져오기와 원문 변경 검출 |
| CSV | 대본 전체를 검증·미리보기 후 교체하는 편집용 CSV | 번역 표와의 연결. 현재 대본 CSV를 완성된 번역 파이프라인으로 설명하지 않는다. |

## 3. 다음 제작 순서

1. **상태와 문장 ID의 기준부터 정한다.** 실제로 이후 반응에 쓰는 사실만 기록한다. 메인 단계와 독립 선택을 구분하고, 서로 배타적인 상태를 여러 bool로 중복 표현하지 않는다. 키는 내부 식별자이며 제작창에서는 이름·설명으로 고르게 한다.
2. **번역의 빈 부분을 막는다.** 본문·선택지·이름에 고정 ID와 기본 문구를 사용한다. 현재 번역 로더의 물리적 줄 단위 CSV 분리를 보완하고, 다중 행 셀·누락 번역·변수 자리표시자·텍스트 효과 태그를 검사한다. 모든 언어 번역을 지금 완료할 필요는 없다.
3. **NPC 한 명의 상태별 반응을 연결한다.** 등장 조건/장소/대화/우선순위를 한 목록으로 관리한다. 위치가 바뀐 상태와 눈앞에서 이동하는 연출을 구분한다. 여러 후보가 동시에 나타나지 않게 검증한다.
4. **사건 하나를 기존 시퀀스에 연결한다.** 조건 판단은 상태를 바꾸지 않는다. 대화 선택 결과를 받아 필요한 부분만 분기하고 공통 진행으로 합친다. 스토리 시퀀스가 전투를 시작한다면 대화 선택지에서도 같은 전투를 중복 시작하지 않게 실행 주인을 하나로 정한다.
5. **완료/취소/재진입/저장·로드를 마감한다.** 선택한 사실과 사건 완료를 별개로 기록한다. 정상 완료하지 않은 사건을 완료 처리하지 않는다. 중간 저장을 지원하지 않는다면 안정된 사건 전후만 저장 지점으로 명확히 안내한다. 보상이나 일회성 결과가 중복 적용되지 않아야 한다.

시퀀스 메이커 자체 재설계, 새 범용 퀘스트 엔진, 전체 NPC 일정 시뮬레이션, 모든 언어 번역은 우선 범위에서 제외한다. 먼저 기존 부품이 실제 한 장면에서 이어지는지 확인한다.

## 4. 첫 완성 기준: Windmill의 작은 구간

목표 규모는 방 1개, NPC 1명, 선택지 2개, 상태별 대화 2~3개, 짧은 사건 1개다. 아래는 검증 목표이며 현재 통과 기록이 아니다.

- 메이커로 방과 NPC·대화를 연결하고 실행할 수 있다.
- 최초 대화와 재대화가 의도대로 다르며, 특정 선택 후 반응이 바뀐다.
- 사건 연출이 완료된 뒤 재입장해도 처음부터 반복되지 않는다.
- 사건을 중단하면 완료로 잘못 기록되지 않고 입력/카메라가 복구된다.
- 저장·불러오기 후 NPC의 대사와 출현 상태가 일치한다.
- 한국어/영어 전환 시 본문·선택지·이름이 모두 표시된다. 미번역 기본 문구 정책도 확인한다.
- 누락된 대화·잘못된 조건·중복 ID를 제작 단계에서 알아볼 수 있다.

게임 전체가 미완성이어도 이 구간은 시작부터 종료까지 설명하고 반복 시연할 수 있는 상태로 만든다. 기능 개수를 늘리는 것과 완성도를 높이는 것을 혼동하지 않는다.

## 5. 공부 방식

한 기능마다 다음 기록을 짧게 남긴다.

1. 해결하려는 불편과 기존 방식의 실패 사례.
2. 실제 호출 경로와 데이터의 주인. 버튼 → 검증 → 데이터 변경 → 런타임 반영까지 설명한다.
3. 선택한 설계와 선택하지 않은 대안, 각각의 비용.
4. 직접 수행한 작은 수정 한 가지와 수정 전후 동작.
5. 의도적으로 잘못된 입력을 넣었을 때의 결과, 남은 한계.

AI 도움은 초안/설명/리뷰 등 사용 범위를 기록한다. 학습 완료 기준은 코드를 읽었다는 사실이 아니라, AI 없이 핵심 흐름을 설명하고 작은 요구 변경이나 오류를 직접 처리할 수 있는지다. 기존 선배 구현을 이해·연결한 것과 직접 설계·구현한 것은 구분한다.

병행할 기초는 C# 값/참조·컬렉션·예외·이벤트 수명, Unity 직렬화·Prefab·씬 수명, 자료구조/알고리즘이다. 성능은 추측 대신 Profiler로 확인한다. C++/Unreal 직무를 목표로 하면 해당 언어·엔진 역량을 별도로 준비한다.

## 6. 면접에 사용할 수 있는 기술 사례

현재 코드를 포트폴리오 소재로 사용할 수 있다는 판단이지, 특정 회사 합격이나 완성도 인증은 아니다. 게임 클라이언트·제작 도구 직무를 우선 가정한다. 일반 웹/서버나 엔진·렌더링 직무에는 요구 역량과의 차이가 있다.

| 사례 | 설명할 문제와 설계 | 준비할 증거 |
| --- | --- | --- |
| 맵 제작 | 분산된 Prefab/방/구역 데이터를 일관되게 생성하고 ID/참조를 연결. 임시 씬과 생성분 한정 복구 | 생성 전후 데이터, 실패 사례, 수동 작업과 도구 작업 비교 |
| 대사 CSV | 잘못된 외부 대본이 기존 자산을 손상하지 않게 전체 검증·미리보기·원본 변경 확인 후 적용 | 여러 줄/따옴표/한글 사례, 잘못된 참조 차단, 실제 실행한 검사 기록 |
| 안전한 삭제 | 삭제 범위 제한, 외부 참조 확인, 실행 직전 재검증, 부분 실패 보고 | 참조된 방의 삭제 차단, 미리보기 후 변경, 휴지통 복구 절차 시연 |
| 상태별 스토리 | 저장 사실과 NPC 반응/사건 실행을 분리 | 향후 완성할 작은 플레이 구간과 저장·로드·취소 결과 |

관련 구현: [맵 서비스](../../../Assets/_Game/Scripts/Editor/ContentMaker/Maps/ContentMakerMapService.cs), [CSV 처리](../../../Assets/_Game/Scripts/Editor/ContentMaker/Dialogue/ContentMakerDialogueCsv.cs), [삭제 서비스](../../../Assets/_Game/Scripts/Editor/ContentMaker/Maps/ContentMakerDeletionService.cs).

현재 한계도 같이 설명해야 한다. 정적 컴파일 성공은 Unity 동작 검증이 아니다. 테스트 소스가 있다는 것과 테스트를 실행해 통과했다는 것은 다르다. 삭제 검사는 동적 문자열을 완전히 증명하지 못하고 스냅샷은 파일 길이·수정시각·GUID 기반이다. 방 생성 전체는 단일 원자적 파일 트랜잭션이 아니다. 저사양 모바일/스위치에서 성능을 달성했다는 실측 근거도 아직 이 기록에는 없다.

## 7. 포트폴리오 묶음

- 개요 1쪽: 팀 규모/기간, 게임의 목표, 현재 완성 범위, 본인 역할.
- 짧은 시연: 콘텐츠 제작 → 실제 게임 반영 → 상태 변화. 영상 길이는 약 2~3분을 첫 목표로 하되 회사 제출 형식을 우선한다.
- 기술 사례 2~3개: 문제 → 설계 → 코드 → 실패 대응 → 검증 결과 → 한계.
- 재현 가능한 실행 방법과 필요한 버전, 코드 발췌 또는 접근 가능한 저장소.
- 기여 구분: 선배/팀의 기존 기반, 직접 구현, 직접 개선·검증, AI 보조 범위. 비율을 추측해 기입하지 않는다.
- 측정: 같은 콘텐츠 제작 시간, 누락/오류 건수, 도구의 검색/검사 시간 등 실제 측정한 값만 사용한다. 런타임 성능 수치는 하드웨어·빌드 종류·장면·반복 조건을 함께 기록한다.

팀 코드나 외부 에셋을 공개할 때는 팀 동의와 라이선스를 확인한다. 유료 에셋 원본을 그대로 공개 저장소에 올리지 않는다.

학습용 질문 예시: 왜 ScriptableObject와 Prefab을 나눴는가? 미리보기 후 파일이 바뀌면? 삭제가 일부만 성공하면? 한 조건이 NPC의 위치와 대사를 어떻게 함께 바꾸는가? 번역문 순서가 바뀌어도 같은 문장을 어떻게 식별하는가? 이 도구가 실제로 줄인 작업은 무엇인가?

## 8. 채용 자료와 판단의 경계

Epic의 공식 안내는 프로그래밍 전문 분야에 Tools Development를 명시하고, 포트폴리오에는 본인의 기여·성과와 가장 잘 마감된 작업을 명확하게 보여주도록 안내한다. 따라서 제작 도구도 면접 소재가 될 수 있다는 근거는 있으나, 이것이 미완성 프로젝트만으로 모든 대기업의 기준을 충족한다는 뜻은 아니다. [Epic 공식 커리어 안내](https://www.epicgames.com/site/earlycareers/career-paths?lang=en)

같은 안내에서도 Epic의 프로그래밍 분야는 C++/Unreal과 자료구조·알고리즘 기초를 강조한다. Unity 프로젝트의 도구 설계 경험이 다른 기술 스택의 실무 숙련을 자동으로 대신하지는 않는다. 지원 직무별 요구사항에 맞춰 자료를 조정한다. [Epic 프로그래밍 안내](https://www.epicgames.com/site/earlycareers/career-paths?lang=en)

국내 개별 공고는 이번 확인에서 공식 본문을 충분히 확보하지 못해 특정 회사의 현재 모집 요건이나 미완성 프로젝트 허용 기준을 단정하지 않는다. 위 포트폴리오 구성과 학습 순서는 현재 프로젝트를 바탕으로 한 권고다.
