# 전투·상태·스킬·장비·UI 논의

상태: 2026-09-07 상담 및 후속 승인 기록. 아래 비교 시안은 미확정 자료다. 이후 사용자가 **Z 시간제 방어 / 퍼펙트 패링의 Unity 구현**을 승인해 반영했다. 격자는 추후 특정 전투로 보류했고, 상태·스킬·장비·전체 UI 제안은 여전히 확정되지 않았다. 현재 방어 구현·조정 위치·검증 한계는 [구현 기록](../../../docs/superpowers/plans/2026-09-07-timed-guard.md)을 참고한다.

## 사용자 의도

- 공격과 패링이 메인 전투다. 패링/회피/점프 유지와 같은 버튼의 방어/퍼펙트 패링을 비교 중이다.
- 보충 조건: 일반 방어도 어느 정도 타이밍이 필요하고 일부 피해를 받는다. 퍼펙트 패링에는 반격 또는 별도 보상이 있다. 단순 상시 홀드 방어로 해석하지 않는다.
- 버프·디버프의 적정 복잡도와 림버스 계열 상태 표시, 다인 파티의 스킬 창, 쯔꾸르형 장비 템플릿, 언더테일과 구분되는 UI를 고민한다.

## 현재 코드에서 확인한 제약

1. `SkillTreeDefinition.MaximumEquippedSkills` 기본값과 `Player_SkillTree.asset`은 6. 배우는 수와 전투에 장착하는 수를 구분할 기반이 있다.
2. AP는 공통 자원이며 주인공 전용 압력·과열 루프는 현재 검색에서 확인하지 못했다. 스탯/자원 추가를 자동 결정하지 않는다.
3. 현 QTE는 패링/회피/점프의 새 입력을 받아 판정을 끝낸다. 홀드 입력·유효시간·재시도 정책 변경은 단순 키 설정 변경이 아니다.
4. 적 스킬에는 `JumpOnly` 등 방어 요구가 있으므로 단일 입력 결정 시 관련 공격 데이터도 대응 방식을 다시 정해야 한다.
5. 현재 상태효과는 `Stacks`와 `DurationTurns`이며 동일 효과 재적용은 기본 중첩 추가와 지속시간 max. 위력/발동 횟수의 두 독립 자원을 이미 지원한다고 표현하지 않는다.
6. Factory의 효과 ID는 9개이고 일부 행동 연결이 미완이다. 파티 슬롯은 주로 HP/AP/초상화/이름을 다루며 상태 아이콘·숫자·상세설명 표시 계약은 보강 대상이다.
7. 장비는 무기/장신구1/장신구2/머리/몸/신발 6칸. 스탯 적용과 장착 검사는 있지만 `PassiveEffectID`/`EquipReactionDialogueID`의 실제 소비는 확인되지 않았다.
8. 전열이 바뀌면 같은 파티 UI에 새 전열을 연결한다. 수동 교대가 없으며 후열 3명의 모든 스킬을 상시 노출할 필요는 없다.

## 논의용 추천 방향

- 방어: 타이밍 손맛을 주축으로 선택한다면 넓은 방어 구간/좁은 퍼펙트 구간의 단일 입력안을 우선 비교한다. 오래 미리 누르기·연타로 판정을 상시 유지할 수 없도록 유효시간/재입력 규칙을 정해야 한다. 여러 방어 유지안은 공격 종류를 읽고 대응 수단을 고르는 재미를 간판으로 삼을 때 적합하다.
- 상태: Chapter 1에서 사용하는 공용 효과를 우선 6~8종 정도로 한정하는 제안. 기존 효과 삭제나 개수 상한 확정이 아니다. 위력/중첩/기간 중 무엇을 숫자로 보여 주는지, 재적용·소모 시점·방어 성공 시 부여 여부를 명시한다.
- 상태 UI: 평소 중요한 아이콘과 남은 턴/횟수, 선택 시 이름·정확한 효과·소모 시점. 패드/터치에서도 열 수 있는 공통 상세 영역을 사용하고 마우스 hover만 전제하지 않는다. 요약에서 생략한 효과는 +N 등으로 존재를 알린다.
- 스킬: 배우는 수와 전투 장착 수 분리. 현재 6개 장착 기반을 활용할 수 있으며 Chapter 1 제공 수는 별도 결정. 스킬 선택은 현재 행동자만, 후열은 축약 정보. 각 스킬이 다른 사용 상황을 갖도록 작성한다.
- 장비: 기존 슬롯과 스탯 보정부터 제작한다. 장비 기획 템플릿은 슬롯/장착 대상/수치/고유 효과/입수 시점/설명/아이콘을 포함하되 미구현 고유 패시브를 이미 지원하는 것처럼 입력하지 않는다.
- UI: 행동 선택 중에는 계획 정보, 적 공격 중에는 공격 예고·방어 판정·피격 대상에 집중시키는 두 정보 수준을 제안한다. 후속 요청에 따라 웹에서 두 방어 방식과 화면 방향을 비교했으며 Unity의 기존 레이아웃은 변경하지 않았다.

사용자 보충: 공격은 1~5개 포즈와 코드 이동을 조합한다. 턴제 RPG를 유지하면서 일방적으로 맞는 느낌을 완화하는 것이 목표다. 마우스 없이 상태 설명을 확인해야 하며, Unity 코드 대신 웹 비교 결과물을 요청했다.

- 시안 원본: `C:/Users/taehw/.codex/visualizations/2026/07/23/019f8ebc-d983-7903-94f2-0c51e8526cba/hub-to-home-combat-options.html`.
- 비교 A: 같은 버튼의 타이밍 방어/퍼펙트 패링. 미리 계속 누르기는 실패, 일반 방어는 유효 구간의 새 입력 후 타격까지 유지. 좁은 구간의 새 입력은 퍼펙트. 일반 방어 시연 G, 퍼펙트 시연 P, 직접 시도 Space/Z.

### 이번 상담의 우선 권고

현 목표에는 A를 먼저 비교할 가치가 크다. 공격의 차이는 버튼 가짓수뿐 아니라 전조 길이, 연속 타격 간격, 대상, 공격 후 빈틈으로도 만들 수 있다. B를 채택한다면 희소 포즈만으로 하단/관통/일반을 구분하도록 강요하지 말고 일관된 모양·효과음·예고를 함께 설계해야 한다. 타이밍 표시줄은 웹 비교를 위한 도구이며 본편 상시 UI 확정이 아니다.

일반 방어로도 적정한 회복 자원을 사용해 진행할 수 있게 하고 퍼펙트는 효율 보상으로 두는 후보를 권한다. 방어 성공에도 전투마다 과도한 회복이 필요하면 사실상 퍼펙트를 강제하므로, 단일 피격 감소율뿐 아니라 연속 공격 총 피해/전투 길이/회복 비용을 함께 봐야 한다.

공용 상태는 Chapter 1에서 6~8종 정도를 먼저 사용해 보고, 기존 상태효과의 행동 연결을 확인한 다음 늘리는 편이 낫다. 화면의 주 숫자 의미를 남은 턴으로 고정하고 중첩 수와 발동 시점은 상세에 분리한다. 공용 효과와 캐릭터 고유 자원을 섞지 않는다. 기존 Stacks/DurationTurns 체계를 림버스의 위력/횟수로 조용히 바꾸지 않는다.

스킬은 장착 수를 늘리기보다 각 선택의 사용 상황을 분리한다. 기본 공격의 AP 수급, 단일/전체/준비/방어 지원/상태 연계의 역할이 겹치지 않는지 확인한다. 장비는 스탯 보정부터 제작하고 미연결 PassiveEffectID를 완성 기능으로 전제하지 않는다.

- 게임 코드·자산·설정 변경, Unity Play/Refresh/컴파일/테스트, 커밋·푸시, 외부 서비스 게시 없음. 웹 시안과 상담 기록만 추가·갱신했다. 정식 구현 승인이나 최종 게임 규칙으로 간주하지 않는다.

## 후속: 스킬 구성과 제작 흐름 정리 (제안, 미구현)

초기 “스킬 구성 만드는 것도 정리” 요청을 아군 스킬 설계와 제작 순서로 해석했으나, 사용자는 이후 **현재 만든 스킬 구성 기능의 확인**이라고 명확히 했다. 아래 구성 제안은 승인되지 않았으며 현재 작업의 결론이 아니다. 실제 검토 결과는 뒤의 ‘현재 스킬 구성 기능 점검’을 따른다. 코드·자산 변경 승인은 없었다.

### 현재 확인된 제작 구조

- Project 창 `Create > Hub To Home > 전투 > 스킬 데이터`에서 SkillData를 만들고 Odin Inspector의 전투 블록 목록을 편집한다. 독립 스킬 메이커 창은 아니며 콘텐츠 메이커는 챕터/마커/대사 영역이다.
- SkillData에는 ID·이름·설명·아이콘·사용 범위·APCost·대상·전체 여부·ActionTimeline이 있다. 이동/애니메이션/피해/상태이상/QTE/VFX/방어창/투사체/순차 근접 공격 블록이 있다.
- 학습·장착은 `CharacterData.SkillTree`의 노드에 SkillData를 연결한다. `MaximumEquippedSkills` 기본값은 6이며 조정 가능하다. 초기 목록에는 `CharacterData.DefaultSkills`도 사용한다.
- 저장된 장착 ID의 런타임 복원을 위해 `GameContentCatalog.Skills` 등록을 확인한다. 전투 메뉴는 현재 행동자의 스킬을 2열·3행 표시와 스크롤, 고정 설명 영역으로 보여준다.
- AP는 각 캐릭터가 보유한다. “공통 자원”은 모든 캐릭터가 같은 종류인 AP를 사용한다는 뜻이지 파티 전체 공유 잔고라는 뜻이 아니다.

### 권고안과 대안

- 권고: 캐릭터 고유 스킬을 배우고 최대 6개 장착하는 기존 구조 유지. Chapter 1은 캐릭터당 3~4개부터 역할 차이를 검증한다. 완성판 총 스킬 수는 지금 확정하지 않는다.
- 대안 1: 소수 고정 스킬만 성장시킨다. 제작·학습 부담은 작지만 조합 선택 폭이 좁다.
- 대안 2: 전원 공용 스킬이나 자유 조립을 중심에 둔다. 조합 폭은 크지만 캐릭터 차별화·설명·밸런스 비용이 늘어 지금은 권하지 않는다.
- 초반 구성 기준은 저비용 주력 / 다른 적 구성에 대응하는 공격 / 동료와 연결되는 효과 / 비용이나 준비 부담이 있는 결정타다. 모든 캐릭터에게 이 네 역할을 똑같이 주라는 뜻은 아니다. 회복·보호 캐릭터는 역할을 대체한다.
- 위젤 샘플에는 압력 베기, 쌍압 절단, 증기 횡단, 압력 해방 등 공격 데이터가 이미 있다. 완성 스킬로 승인된 것은 아니다. 이름·연출·타수만 다른 상위 공격을 늘리기보다 각각 “언제 이 기술이 더 유리한가”와 불리한 상황을 먼저 정한다. 연타가 단타보다 유리하다는 규칙은 적/상태/피해 공식의 근거 없이 가정하지 않는다.
- 공격 스킬의 입력 변경은 이번 제안에서 확정하지 않는다. 향후 입력을 정리한다면 대부분은 짧게, 핵심 타격의 Z 입력은 추가 보상으로 두고 지원 스킬마다 QTE를 강제하지 않는 방향을 비교한다.

### 스킬 한 개 작성 순서

1. 사용 상황을 한 문장으로 쓴다.
2. 대상, 기본 효과, 비용/불리한 점, 성공 보너스를 정한다. 기본 효과 1개와 보조 효과 1개 이내부터 시작한다.
3. 기존 SkillData를 복제한다면 고유 SkillID·사용 범위·APCost·대상/IsAoE를 먼저 확인한다.
4. 아군 공격은 이동 → 예비 동작 → 필요 시 QTE → 타격 모션/VFX/피해 → 복귀로 구성한다. 적 공격은 전조 → 공격과 동기화한 방어창 → 피해 → 복귀이며 방어창의 시간값은 공격별로 확인한다.
5. 카탈로그 등록과 캐릭터 초기 스킬 또는 학습 노드를 연결한다. Inspector 검사 후 실제 캐릭터의 장착 목록에 나타나는지 직접 확인한다.

### 제작 전 주의점

- SeamlessBattleHost 프리팹은 `_apPerTurn: 5`, `_apOnParryPerfect: 20`이다. AP 20 비용은 회복량만 비교하면 퍼펙트 한 번 또는 턴 회복 네 번분이다. 보유 AP/전투 길이는 별도 변수다. 일반 방어만 해도 핵심 스킬이 순환하도록 비용·기본 회복을 설계하고 퍼펙트는 빈도/효율 보상으로 둔다.
- 공통 회복/해제/표식/조건부 보너스를 모두 현재 블록에서 바로 만들 수 있다고 안내하지 않는다. 별도 회복 블록은 현재 SkillActionBlocks에 없고, 상태 부여는 StatusEffectFactory의 등록 ID만 받는다. 기본값 `Sleep`은 현재 factory에 없으므로 그대로 쓰면 경고 후 미적용이다.
- Action_Damage는 사용한 QTE 배율을 다음 피해 블록까지 유지하지 않고 소비 후 초기화한다. 연타 전체에 보너스를 주는 기획이면 현재 실행 순서를 확인해야 한다.
- 스킬이 없는 캐릭터는 BattleMenuUI의 `_exampleSkills` fallback을 쓸 수 있다. 확인한 공용 Host 프리팹의 목록은 비어 있어 그 프리팹에서는 NO SKILL이 표시된다. 모든 씬에서 실제로 샘플이 나타나는 버그라고 단정하지 않는다.
- 직전 방어의 읽기 검토에서 별도 경계 발견: QTEManager가 impact deadline 확인 전에 ObserveHeld를 호출해, 타격 직후~다음 프레임 사이의 해제가 이전 타격의 일반 방어를 취소할 가능성이 있다. 소스 기준 위험이며 실제 재현은 하지 않았다. 이번 스킬 정리 범위에서는 수정하지 않았다.

근거: `Battle/Data/SkillData.cs`, `Battle/Data/SkillActionBlocks.cs`, `Characters/Data/SkillTreeDefinition.cs`, `Characters/Runtime/SkillTreeProgressionService.cs`, `Characters/Runtime/StatusEffectFactory.cs`, `UI/Runtime/BattleMenuUI.cs`, `UI/Runtime/BattleSubMenu.cs`, `Core/Data/GameContentCatalog.cs`, `Battle/Data/SkillDatabase.cs`, `Content/Battle/Prefabs/System/SeamlessBattleHost.prefab`. Scripts 경로는 `Assets/_Game/Scripts/` 기준이다. 브랜치 `codex/gameplayEdit`, 코드/자산/테스트/Unity 실행/커밋·푸시 없음.

## 현재 스킬 구성 기능 점검 — 소스 검토, 미수정

요청 범위는 기존 Odin Inspector/SkillData의 블록 조립, 실제 샘플, 실행·학습·장착 연결을 확인하는 것이다. 새 스킬 기획이나 메이커 재작성은 하지 않는다. `SkillData → ActionTimeline → 캐릭터 초기/학습 스킬 → 카탈로그 기반 저장 복원 → 전투 메뉴` 구조는 유지할 수 있다.

### 우선 수정 후보

1. **제브 고속참·환영호참의 방어창 누락.** `Enemy_ZEV.asset:56–57`에 등록된 `Skill_BlinkSlash.asset:24` 이후의 타임라인에는 피해 1.8배, `Skill_PhantomArc.asset:24` 이후에는 피해 1.2배/1.9배가 있으나 `Action_DefenseWindow`가 없다. `BattleTurnQteModuleControllerService.cs:242`의 스킬 분기는 기본 공격 방어창을 거치지 않고 그대로 실행한다. 따라서 해당 기술이 선택되면 새 Z 방어를 받을 창이 없다. 의도적으로 방어 불가인 특수 공격이라는 별도 승인/규칙은 확인되지 않았다. 검사는 방어창/피해 개수를 세지만 선후 연결이나 누락은 판정하지 않는다(`EnemyAttackAuthoring.cs:287`).
2. **연참의 일반 가드 구간 소실.** `Skill_ComboSlash.asset:114,133,152`의 TimeWindow는 각각 0.1초이고 개별 timing override가 없다. 공용 `SeamlessBattleHost.prefab:5978`의 Perfect 0.12초는 `DefenseTimingProfile.Normalize`에서 창 전체인 0.1초로 제한된다. 유효 새 입력이 들어오면 모두 Perfect가 되어 일반 가드와 피격의 완충 구간을 경험할 수 없다. 기존 데이터를 새 규칙에 맞춰 조정하고, 유효 Perfect가 창 전체를 덮는 설정을 제작 단계에서 알려 주는 것이 우선이다.
3. **전체 대상 해석이 호출 경로마다 다름.** 일반 플레이어 스킬의 대상 선택/실행은 `IsAoE`만 본다(`BattleTurnQteModuleControllerService.cs:549,745`). 적 스킬과 `battle.skill.timeline`의 기본 대상 계산은 `IsAoE || TargetType == AoEAll`을 쓴다(동 파일:944, `BattleSkillTimelineRunner.cs:240`). `AoEAll`만 지정한 동일 데이터가 한 경로에서는 단일, 다른 경로에서는 전체가 된다. 적 스킬의 대상 계산은 AllyOnly도 반영하지 않아 적 지원 스킬을 구성하면 플레이어 측으로 향한다. 우선 대상 의미를 한 곳에서 일치시켜야 한다.
4. **상태이상 블록 기본값과 검사 누락.** `Action_ApplyStatus.StatusID` 기본값은 `Sleep`(`SkillActionBlocks.cs:342`)이나 `StatusEffectFactory`에 없다. 그대로 추가하면 전투에서 경고만 출력되고 효과는 적용되지 않는다. 검사기는 `Action_ApplyStatus`의 ID/턴을 검사하지 않으며, 콘텐츠 검사도 스킬에는 그 분석 결과를 위임한다. 등록 ID 선택과 유효성 검사가 필요하다. Sleep이라는 새 효과를 자동 추가하라는 뜻은 아니다.

### 오류와 구분해야 할 사용 주의점

- QTE 배율은 `Action_Damage` 한 블록이 소비하고 초기화한다(`SkillActionBlocks.cs:330`). 같은 블록의 여러 대상에는 적용되지만 뒤의 별도 피해 블록에는 이어지지 않는다. ‘한 번의 QTE가 연타 전체를 강화’하는 기능으로 안내하면 안 된다. 기존 계약을 바꾸기보다 블록 설명에 범위를 분명히 쓰는 것이 먼저다.
- 이동/투사체 블록은 중간 중단 시 자체 finally 정리가 없다. 특히 투사체는 `WaitForCompletion` 뒤에서만 반환하므로(`SkillActionBlocks.cs:848`) 그 전에 전투 코루틴이 중지되면 자기 수명 처리가 없는 프리팹이 풀에 활성 상태로 남을 위험이 있다. 실제 프리팹의 수명 처리 및 중단 재현은 이번에 검증하지 않아 확정 실행 버그로 승격하지 않는다.
- 직전 통합 방어의 release 샘플링 경계(`QTEManager.cs:179`)는 별도 미수정 사항으로 유지한다. 논리 타격 후 다음 프레임의 해제가 이전 타격 방어에 반영될 수 있다는 소스 위험이며 실행 재현은 하지 않았다.

### 검증/인계

실제 C# 분기, ScriptableObject 타임라인/연결 GUID, 호스트의 timing 설정을 읽고 교차 검토했다. 2열·3행+스크롤 스킬 목록과 트리 장착 제한의 연결은 소스로 확인했으며 UI 실기 검증을 뜻하지 않는다. 새 컴파일·Unity Play·테스트 실행·코드/자산 수정·커밋·푸시는 하지 않았다. 변경은 이 상담/검토 문서와 일일 기록이다. 브랜치 `codex/gameplayEdit`.

## 전용 스킬 메이커 구현 완료

사용자가 별도 창을 선택하여 **Hub To Home → 제작 → 스킬 메이커**를 추가했다. 앞선 검토 시점의 ‘별도 메이커 없음’은 이 구현 이전 상태다. 기존 SkillData/ActionTimeline을 그대로 편집하며 Inspector도 계속 사용할 수 있다.

### 바로 사용하는 순서

1. 메뉴에서 스킬 메이커를 연다. 왼쪽에서 이름·ID·폴더로 검색하거나 아군/적/공용 필터로 기존 스킬을 선택한다.
2. 새로 만들 때는 **새 스킬**을 누르고 `Assets/_Game/Content` 안에 저장한다. 비슷한 스킬로 시작하려면 원본을 저장한 뒤 **스킬 복제**를 누른다. 복제본에는 새 ID가 지정된다.
3. **기본 정보**에서 이름·설명·아이콘·AP·대상을 입력한다. 기존에 연결한 스킬의 ID는 함부로 바꾸지 않는다.
4. **실행 블록 → 블록 추가**에서 이동·애니메이션·대기·피해·QTE·방어/패링 등 기존 블록을 선택한다. 목록의 한 블록을 클릭해 세부값을 편집한다. ↑/↓로 순서를 옮기고 복제/삭제한다. 블록 조작은 Ctrl+Z로 취소한다.
5. **검사 · 시간축**에서 기존 검사 결과와 예상 실행 순서를 확인한다. 경고의 ‘N번 블록 보기’로 해당 블록에 이동한다. `+`는 가변 시간, `?`는 시간 계산 미지원이다.
6. **변경 저장**을 누른다. 선택한 스킬만 저장한다. 새 스킬은 실제 캐릭터의 초기 스킬/스킬 트리에 연결하고 저장 복원용 카탈로그 등록도 확인한다. 이 연결은 자동으로 바꾸지 않는다.

### 저장·안전 범위

- 스킬을 선택만 해서는 저장하거나 자산을 생성하지 않는다. 변경 표시 `●`가 남아 있으면 저장이 필요하다. 창을 닫아도 실제 자산의 메모리상 변경은 남지만, 디스크 보존은 저장 버튼으로 확정한다.
- 블록 깊은 복제는 내부 데이터는 분리하고 Sprite/Prefab 같은 Unity 자산 참조는 유지한다. 스킬 전체 복제는 **저장된 원본** 기준이므로 수정 중에는 복제 버튼을 잠근다.
- 기존 경로 덮어쓰기, 콘텐츠 폴더 밖 저장, 읽기 전용, Play 중 편집을 차단한다. 불필요한 전체 프로젝트 저장·자동 카탈로그 생성은 하지 않는다.
- 한글 기본 정보와 선택형 블록 목록, 회색·청록/밝은 테마를 적용했다. 블록 내부 세부 필드는 기존 Odin 작성 속성/명칭을 유지한다.
- 검사 화면은 기존 분석기를 연결한 것이며 앞서 지적한 방어창 누락·퍼펙트 범위·대상 불일치·상태 ID 문제를 모두 탐지하거나 수정하지 않는다. 기존 전투 로직·수치·자산은 그대로다.
