패링/회피/점프 방어 시스템 리뷰

목적: 33원정대식 "예고 → 짧은 반응창 → 성공 보상 / 실패 피격" 감각을 기준으로 현재 SkillData 기반 방어 구조를 검토했습니다. 이 문서는 의견 정리용이며 코드 수정은 포함하지 않습니다.

현재 방향 SkillData.ActionTimeline과 Action_DefenseWindow 구조는 목표한 전투 감각을 만들기 좋은 출발점입니다.
가장 큰 위험 성공 방어 후에도 일부 공격 블록에서 최소 1 데미지가 들어갈 수 있습니다.
우선 정리 대상 예고 시간, 입력창 시간, 요구 입력, 성공/실패 결과를 하나의 계약으로 통일해야 합니다.

1. 성공 방어 후 최소 1 데미지 가능성

P1

성공 방어가 일부 스킬 블록에서 완전 무효화되지 않을 수 있습니다.

Action_DefenseWindow는 성공 시 CurrentDamageMultiplier = 0f로 만듭니다. 하지만 Action_Projectile과 Action_SequentialMelee는 0으로 계산된 데미지를 그대로 TakeDamage()에 넘깁니다. CharacterBase.TakeDamage()는 최종 데미지를 최소 1로 보정하므로, 플레이어 입장에서는 "패링/회피/점프 성공했는데 1 데미지"처럼 보일 수 있습니다.

추천 방향: 모든 공격 블록이 CurrentDamageMultiplier <= 0일 때 데미지 호출 자체를 건너뛰도록 계약을 맞추는 것이 좋습니다.

2. TelegraphThenNextTurnWindow 모드의 함정

P1

현재 모드 2는 "이번 턴 예고만"이라는 이름과 다르게 뒤 블록이 계속 실행될 수 있습니다.

Action_DefenseWindow가 TelegraphThenNextTurnWindow일 때는 예고를 보여주고 자기 블록만 종료합니다. 하지만 BattleManager.ExecuteEnemySequenceSkill()은 다음 타임라인 블록을 계속 실행합니다. 따라서 뒤에 Action_Damage가 있으면 "예고만 해야 하는 턴에 데미지까지 들어가는" 상태가 될 수 있습니다.

현재 ZEV 관련 에셋들은 PatternMode: 0이라 즉시 문제는 아닙니다. 다만 담당자가 모드 2를 선택하는 순간 재현될 수 있는 구조적 함정입니다.

추천 방향: 모드 2를 유지하려면 타임라인 전체 중단 플래그를 명시하거나, 예고용 블록과 실제 판정 블록을 분리하는 쪽이 안전합니다.

3. 예고 시간과 입력창 시간의 의미 불일치

P2

에셋 설정은 "예고 후 입력창"처럼 보이지만, 코드에서는 예고 VFX와 입력창이 거의 동시에 열립니다.

현재 일반 모드에서는 DefenseOpenDelay만큼 먼저 기다린 뒤 SpawnTelegraph()와 StartDefenseQTE()를 시작합니다. 반면 TelegraphDuration은 모드 2가 아니면 사실상 의미가 약합니다. 담당자가 에셋에서 TelegraphDuration, DefenseOpenDelay, TimeWindow를 나눠 넣어도 실제 체감은 기대와 다를 수 있습니다.

4. 기본 공격은 입력 종류를 검사하지 않음

P2

기본 적 공격은 타이밍만 맞으면 패링/회피/점프 어느 입력이든 성공 처리됩니다.

스킬 쪽은 Action_DefenseWindow.IsMatch()에서 요구 입력을 검사합니다. 하지만 기본 근접 공격 경로는 finalGrade == Miss만 실패로 보고, 그 외 입력은 모두 성공 처리합니다. 33원정대식 감각을 목표로 한다면 공격별 요구 행동이 있어야 합니다.

추천 방향: 기본 공격도 EnemyAttackType이나 별도 DefenseRequirement를 통해 요구 입력을 검사하도록 맞추는 것이 좋습니다.

5. 입력 표기 불일치

P2

실제 키 매핑과 주석/문서가 어긋나 있습니다.

실제 입력은 GameInput 기준 Z = Parry, X = Dodge, C = Jump입니다. 그런데 BattleStateMachine 주석에는 회피가 C, 점프가 Space로 적혀 있습니다. 담당자가 주석을 믿고 에셋이나 UI 문구를 만들면 테스트가 헷갈릴 수 있습니다.

추천 방향: 현재 결정이 Z / X / C라면 enum 주석, UI 라벨, 기획 문서, QTE 설명을 같은 표기로 통일해야 합니다.

6. QTE 등급 활용이 약함

P3

Perfect, Great, Good, Bad를 계산하지만 결과 차이는 거의 없습니다.

QTEManager는 등급을 계산합니다. 하지만 현재 스킬 방어는 Miss만 아니면 성공이고, 차이는 Perfect Parry의 MP 회복 정도입니다. 손맛을 더 만들려면 등급별로 보상과 리스크를 나눌 여지가 있습니다.

추천 방향: 예를 들어 Perfect Parry는 MP 회복과 반격 기회, Great/Good은 무효화, Bad는 피해 경감 정도로 구분하면 반응형 전투 감각이 살아납니다.

콘솔 메시지 확인

MCP

현재 콘솔의 실제 Error는 게임 코드가 아니라 Packages/com.coplaydev.unity-mcp 쪽 메시지입니다. 내용은 MCP-FOR-UNITY: Client handler error: Cannot access a disposed object.였습니다.

C# 프로젝트 진단은 에러/경고 0개였고, SkillActionBlocks.cs, QTEManager.cs 검증도 깨끗했습니다. 이 메시지는 MCP 클라이언트 핸들러 수명 문제로 보이며, 패링 시스템의 런타임 버그로 보지는 않습니다.

담당자에게 제안하는 다음 액션: 먼저 데미지 무효화 계약과 모드 2 동작을 정리한 뒤, 기본 공격과 스킬 공격이 같은 방어 판정 로직을 쓰도록 통합하는 것을 추천합니다. 그 다음에 33원정대식 손맛을 위해 등급별 보상과 타이밍 값을 튜닝하는 순서가 좋습니다.
