# 07. 직접 해 볼 과제와 면접용 정리

[학습 목차](README.md) · [설계·검증 기준](06-design-patterns-performance-testing.md) · [제작창 사용법](../content-maker-guide.md)

목표는 기능 수를 늘리는 것이 아니라 **내가 이해하고 검증한 변경 하나**를 남기는 것입니다.
아래는 학습 과제입니다. 구현·테스트·성능 측정을 이미 완료했다는 기록이 아닙니다.
학습용 브랜치나 복제 자산에서 시작하고, 팀이 사용하는 원본 대본·저장 데이터를 실험용으로 덮어쓰지 마세요.

## 1. 매 과제의 공통 절차

1. 현재 동작을 한 문장으로 적습니다.
2. 바꾸려는 범위를 한 함수 또는 한 흐름으로 제한합니다.
3. 입력·결과·실패 조건을 먼저 표로 적습니다.
4. 호출자와 데이터 소유자를 확인한 뒤 수정합니다.
5. 컴파일과 구성 검사를 먼저 합니다. 실제 실행이 필요한 항목은 그 이유와 함께 별도로 확인합니다.
6. 전후 차이, 확인하지 못한 항목, 되돌리는 방법을 기록합니다.

처음부터 범용 프레임워크·전면 리팩터링·새 관리자부터 만들지 않습니다.
동일 문제의 실제 사례가 둘 이상 생기고 변경 비용을 설명할 수 있을 때 공통화 여부를 판단합니다.

## 2. 과제 A — 대화 한 번을 따라가기

읽을 곳: [04 대사 흐름](04-scenario-and-dialogue.md), [NPCMarker](../../Assets/_Game/Scripts/Overworld/AreaMarkers/Runtime/NPCMarker.cs), [DialogueManager](../../Assets/_Game/Scripts/Dialogue/Runtime/DialogueManager.cs).

**변경 없이 시작하는 과제입니다.** NPC를 선택했을 때 다음 질문에 함수 이름으로 답해 보세요.

- 누가 상호작용 입력을 감지하고 NPC의 `Interact`를 호출하나요?
- NPC는 직접 문장을 갖고 있나요, DialogueData를 참조하나요?
- 조건 문서가 있을 때 기본 대화와 조건별 대화 중 무엇이 선택되나요?
- 타이핑 도중 확인 입력과 타이핑 완료 후 입력은 어떻게 다르나요?
- 대화가 끝나면 누가 이동 입력·게임 상태를 복원하나요?
- NPC가 사라지거나 다른 대화가 실행 중이면 어떻게 되나요?

완료 산출물: 함수 5~8개를 화살표로 연결한 호출 순서와, 상태 변경 위치 3개.
다른 사람의 설명을 복사하지 말고 코드에서 확인한 메서드명을 적습니다.

## 3. 과제 B — 조건 대화를 데이터만으로 만들기

준비: 같은 NPC의 기본/전투 후 대화 두 문서와 학습용 일반 NPCMarker 하나.

1. 메이커에서 두 대화를 만듭니다. 대사·표정·선택지 동작을 구분합니다.
2. `조건·NPC`에서 기본 대화를 연결한 조건 문서를 만듭니다.
3. 예시 키 `study.npc.talked`, 비교 `같음`, 값 `1`, 전투 후 대화, 우선순위 `10`을 넣습니다.
4. 조건 문서를 저장하고, 선택한 방 PrefabStage의 일반 NPC에 연결·저장합니다.
5. 어떤 코드가 이 키를 언제 변경해야 하는지 찾습니다. 이름만 정했다고 값이 자동으로 바뀌지는 않습니다.
6. 플레이 확인을 직접 할 때는 기존 세이브와 구분한 실험 상태를 사용합니다.

| 상태 | 예상 대화 |
|---|---|
| 플래그 없음 / 값 0 | 기본 대화 |
| 값 1 | 조건 대화 |
| 두 조건이 동시에 맞음 | 더 높은 우선순위 |
| 우선순위까지 같음 | 위쪽에 놓인 조건 |

완료 기준: 위 네 가지 선택 이유를 `FlagDialogueSelector.Resolve`의 비교식으로 설명합니다.
이 과제는 NPC 이동 스케줄·제브의 접근 공격·전체 메인 스토리 분기까지 만드는 과제가 아닙니다.

## 4. 과제 C — 작은 순수 규칙을 직접 검증하기

읽을 곳: [03 스탯·피해·QTE](03-battle-and-characters.md).
첫 연습은 게임 씬 전체보다 입력과 결과가 분명한 계산 하나가 좋습니다.

- 선택 1: ATK의 기초값·장비 고정값·장비 비율·전투 버프를 손으로 계산합니다.
- 선택 2: 조건 대화의 우선순위를 종이의 목록에서 직접 골라 봅니다.
- 선택 3: 방어 입력이 없음/올바름/잘못됨/여러 개임을 판정 표로 정리합니다.

정상 입력 두 개만 확인하고 끝내지 않습니다. 빈 목록, 경계값, 중복, 0, 잘못된 ID를 포함합니다.
경계값 비교가 `<`인지 `<=`인지에 따라 예상 결과가 바뀌는 이유도 설명합니다.

검증 코드를 직접 작성할 때는 해당 프로젝트의 기존 Editor 테스트를 먼저 읽습니다.
작성만 했으면 `테스트 소스 작성`, 실제 실행 로그가 있으면 `실행 결과 확인`이라고 나눠 기록합니다.

## 5. 과제 D — 턴 규칙과 UI 길이를 분리해 생각하기

읽을 곳: [BattleTurnQteModuleControllerService](../../Assets/_Game/Scripts/Battle/Runtime/Services/BattleTurnQteModuleControllerService.cs)의 `RunTurnCalculation`, `AdvanceTurn`. [BattleManager](../../Assets/_Game/Scripts/Battle/Runtime/BattleManager.cs)는 해당 서비스로 위임합니다.

현재 5명 A-B-C-D-E를 8칸에 반복하면 `A B C D E A B C`입니다.
큐가 끝날 때마다 처음부터 만들면 16번 동안 A/B/C는 각 4번, D/E는 각 2번 행동합니다.
이 계산은 해당 코드의 반복 규칙만 가정한 예시이며 실제 전투 결과를 측정한 값은 아닙니다.

먼저 다음 중 게임의 의도를 결정해 보세요.

- 참가자 모두 한 번씩 행동하고 새 라운드를 시작하는가?
- SPD가 순서뿐 아니라 행동 횟수에도 영향을 주는가?
- 같은 SPD는 어떤 순서로 정할 것인가?
- 사망·부활·후열 투입 때 다음 행동자는 누구인가?

그 뒤 **전투 규칙의 순서 상태**와 **화면에 미리 보여줄 길이**를 분리하는 작은 설계를 적습니다. 현재 기본값은 실행 큐 8칸, 화면 표시 4칸이므로 둘을 같은 값으로 혼동하지 않습니다.
바로 힙이나 복잡한 시간 게이지를 도입하는 것이 정답은 아닙니다. 선택한 규칙에 필요한 자료구조부터 고릅니다.
완료 기준: 1/3/5/6명, 중간 사망, 전열 교체, 동속도의 예상 순서를 설명합니다.
이 과제는 현재 코드의 개선 후보이며 이번 정리에서 전투 규칙을 변경하지 않았습니다.

## 6. 과제 E — 에디터 검증 하나 추가하기

읽을 곳: [05 에디터·자산 관리](05-editor-tools-and-assets.md), [조건 대화 패널](../../Assets/_Game/Scripts/Editor/ContentMaker/Dialogue/ContentMakerDialogueRulesPanel.cs).

추천 연습: **조건 목록에서 같은 플래그·비교·값·우선순위를 가진 중복 규칙을 경고**합니다.
두 규칙의 대화가 달라질 수 있으므로 자동 삭제하거나 조용히 합치지 않습니다.

1. 중복으로 간주할 필드와 무시할 필드를 정의합니다.
2. 작은 목록에서는 이중 반복이 충분한지, 큰 목록이면 키 집합이 필요한지 설명합니다.
3. 검증 결과만 표시하고 런타임 자산은 자동 수정하지 않습니다.
4. 조건을 바꾸거나 Undo했을 때 오래된 경고가 남지 않는지 확인합니다.
5. 기존 동점이면 위쪽 우선 규칙은 그대로 보존합니다.

완료 산출물: 중복/정상/빈 키/다른 우선순위 예제와 경고의 정확한 적용 범위.
에디터의 매 프레임마다 전체 프로젝트를 `FindAssets`로 검색하지 않습니다.

## 7. 과제 F — CSV 왕복과 번역 경계를 확인하기

읽을 곳: [ContentMakerDialogueCsv](../../Assets/_Game/Scripts/Editor/ContentMaker/Dialogue/ContentMakerDialogueCsv.cs), [04 번역 경계](04-scenario-and-dialogue.md).

샘플 대본에 쉼표, 큰따옴표, 한글, 여러 줄, 선택지, 표정, 기존 번역 키를 각각 넣습니다.
내보내기 → 외부 편집 → 검사/미리보기 → 적용의 각 단계에서 무엇이 원본인지 적습니다.
같은 대본을 다시 내보냈을 때 비교할 것은 줄바꿈 형식만이 아니라 대사·참조·순서의 의미입니다.

실패 사례도 만듭니다: 잘못된 GUID, 존재하지 않는 화자, 중복 순번, 닫히지 않은 따옴표.
실패 후 원래 DialogueData가 바뀌지 않아야 합니다.
미리보기를 띄운 뒤 Unity 쪽 대사를 바꾸면 재검사가 필요한 이유를 설명합니다.

번역표는 별도입니다. 대본 CSV의 여러 줄 셀 지원을 LocalizationTable 로더에도 있다고 가정하지 마세요.
본문 키, 선택지 문구, 화자 이름을 각각 어디서 처리하는지 구분하면 과제 완료입니다.

## 8. 과제 G — 실패와 정리 경로 한 개 추적하기

읽을 곳: [02 방 전환·저장](02-unity-world-and-services.md), [04 액션 수명](04-scenario-and-dialogue.md).

대화 또는 시퀀스를 하나 골라 정상 완료·취소·대상 파괴·씬 전환을 표로 나눕니다.
각 경우 입력 차단, 카메라 요청, 코루틴/트윈, 완료 콜백이 어떻게 정리되는지 찾습니다.
“Cancel 함수가 있다”는 답으로 끝내지 않고 실제 호출자와 뒤늦은 완료가 다시 들어올 가능성까지 봅니다.

실습용 확인을 직접 한다면 취소 전후 같은 이벤트가 두 번 발생하지 않는지 기록합니다.
수정 범위를 해당 소유자 한 곳으로 제한하고, 다른 시스템의 전역 상태를 무조건 초기화해 해결하지 않습니다.
완료 기준: 자신의 요청만 해제해야 하는 이유와, 전체 리셋의 위험을 사례로 설명합니다.

## 9. 과제 H — 성능 개선을 숫자로 남기기

읽을 곳: [06 성능 측정](06-design-patterns-performance-testing.md).

예시 대상은 상호작용 검사 또는 반복 VFX 생성 중 하나입니다. 둘을 동시에 바꾸지 않습니다.
같은 씬·개체 수·해상도·품질·동작에서 변경 전후를 비교합니다.
에디터에서 컴파일 중인 순간과 기기 빌드의 안정 구간을 같은 표에 섞지 않습니다.

| 기록 | 값 |
|---|---|
| 기기 / OS / Unity / 빌드 설정 | 직접 입력 |
| 재현 조건 / 실행 시간 / 반복 횟수 | 직접 입력 |
| CPU 시간 / GC Alloc / 프레임 시간 분포 | 측정 도구와 함께 입력 |
| 변경 전 → 변경 후 | 실제 수치만 입력 |
| 기능 변화·부작용 | 없다고 추정하지 말고 확인 범위 기록 |

CPU 사용량 하나만으로 발열 개선을 단정하지 않습니다. 렌더링, 프레임 제한, 기기 온도와 전력 조건도 영향을 줍니다.
측정하지 않은 플랫폼은 `미측정`으로 남깁니다. 이번 학습 문서에도 모바일·Switch 성능 보장 수치는 없습니다.

## 10. 포트폴리오로 남길 세 가지 사례

완성되지 않은 게임이라도 **끝까지 설명·검증할 수 있는 범위**를 떼어 기술 사례로 정리할 수 있습니다.
프로젝트의 크기나 패턴 개수 자체가 채용 결과를 보장하지는 않습니다.

| 사례 | 보여줄 문제 | 가져갈 증거 |
|---|---|---|
| 콘텐츠 제작 도구 | 비개발자가 폴더·참조·대사 구조를 잘못 연결하기 쉬움 | 제작 순서, 변경 코드, 검증/Undo 범위, 실패 시 보존 결과 |
| 게임 상태와 실행 수명 | 대화·전투·방 전환이 겹치면 입력과 요청이 남을 수 있음 | 호출도, 소유권, 취소 사례, 재현 로그 |
| 자료구조·성능 | 목록 탐색·생성/반납·상태 갱신의 비용 | 선택 근거, 복잡도 전제, 같은 조건의 실제 측정 |

각 사례는 `문제 → 제약 → 비교한 대안 → 선택 이유 → 구현 → 검증 → 남은 한계` 순서로 설명합니다.
이 구조를 채우지 못한다면 기능을 더 추가하기보다 현재 사례를 먼저 공부합니다.

## 11. 면접에서 스스로 답해 볼 질문

1. 왜 방을 Scene 하나씩이 아니라 Room Prefab으로도 나눴나요? 단점은 무엇인가요?
2. ScriptableObject 원본과 플레이 중 상태를 왜 분리해야 하나요?
3. 대화 선택에 전체 정렬 대신 한 번의 최대값 탐색을 쓰는 이유는 무엇인가요?
4. Dictionary 조회가 항상 최악 O(1)이라고 말할 수 있나요?
5. CSV를 `Split(',')`로 처리하면 어떤 대본에서 실패하나요?
6. Undo와 새 자산 파일 생성 취소, 휴지통 복구는 어떻게 다른가요?
7. 에디터 검증과 런타임 검증은 왜 둘 다 필요하나요?
8. 취소된 코루틴의 늦은 완료를 버전 번호로 막는 것과 스레드 잠금은 어떻게 다른가요?
9. 풀링을 했는데도 메모리가 늘거나 효과가 잘못 남을 수 있는 이유는 무엇인가요?
10. DOTween/Odin이 해결한 부분과 직접 구현한 정책은 각각 무엇인가요?
11. AI가 작성한 부분에서 본인이 찾아낸 문제와 직접 확인한 결과는 무엇인가요?
12. 다시 만든다면 유지할 것 하나와 단순화할 것 하나는 무엇인가요?

## 12. 복사해서 쓰는 학습 기록 양식

```text
날짜 / 브랜치 / 관련 파일:
```
