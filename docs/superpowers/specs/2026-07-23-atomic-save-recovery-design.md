# 저장 데이터 버전·원자적 기록·복구 설계

## 목적

`HUBTOHOME-62`는 현재 본 JSON 파일을 직접 덮어쓰는 `SaveManager`를
강제 종료와 파일 손상에 견디는 저장 기반으로 교체하는 작업이다.

이번 범위는 저장 파일의 신뢰성과 개발 도구에 집중한다. 타이틀의 이어하기 흐름,
스토리 분기 UI, 저장 슬롯 선택 화면은 변경하지 않는다. 기존 호출자인
`SavePoint`, `SavePointMarker`, `TitleMenuManager`가 사용하는
`Save`, `Load`, `Delete`, `Exists`, `HasAnySave` API는 유지한다.

## 현재 문제

- `File.WriteAllText`가 본 파일을 직접 덮어써 중간 종료 시 정상 데이터도 잃을 수 있다.
- 저장 JSON에 스키마 버전이 없어 필드 추가와 구버전 처리를 구분할 수 없다.
- 본 파일이 깨지면 직전 정상본으로 복구할 경로가 없다.
- `Load`는 손상, 미지원 미래 버전, 파일 없음이 모두 `null`로 끝난다.
- 개발자가 슬롯별 본 파일·백업·스키마 상태를 한눈에 확인할 도구가 없다.

## 검토한 접근

### 1. 임시 파일만 사용

같은 폴더에 임시 파일을 쓴 뒤 본 파일로 이동한다. 직접 덮어쓰기보다는 안전하지만
직전 정상본과 구버전 처리 경로가 없다.

### 2. 버전 파이프라인과 본 파일·백업 교체

JSON을 임시 파일에 내구성 있게 기록하고 다시 읽어 검증한 뒤,
기존 본 파일이 정상이면 원자 교체하면서 직전 정상본을 백업으로 남긴다.
로드는 본 파일, 백업, 중단된 첫 저장의 임시 파일 순으로 검사한다.

### 3. 저널·다중 세대 스냅샷

모든 변경을 로그에 기록하고 체크포인트를 만든다. 복구력은 높지만 현재 데이터 규모와
동기식 저장 흐름에는 구현·운영 비용이 과하다.

**채택:** 2번. 한 슬롯당 정상본 두 세대를 유지하면서 기존 사용법을 보존한다.

## 아키텍처

### `SaveData`

- `schemaVersion`을 추가한다.
- 새 스냅샷은 항상 `SaveSchema.CurrentVersion`으로 기록한다.
- 기존 버전 필드가 없는 JSON은 명시적으로 버전 0으로 판정한다.

### `SaveDataCodec`

- JSON 파싱과 스키마 판정을 소유한다.
- 버전 필드가 없는 기존 JSON은 0 → 현재 버전 마이그레이션을 거친다.
- 현재 버전보다 높은 파일은 추측해 읽지 않고 `UnsupportedFutureVersion`으로 거절한다.
- 누락된 문자열·컬렉션은 안전한 기본값으로 정규화한다.
- 빈 객체처럼 저장 데이터로 볼 수 없는 legacy JSON은 손상으로 판정한다.
- Room, SpawnPoint, 파티, 인벤토리, 플래그, Encounter Memory,
  시나리오가 없는 Overworld Enemy 상태를 보존한다.

### `AtomicSaveStorage`

한 슬롯은 같은 디렉터리의 네 경로를 사용한다.

- `save_slot_N.json`: 현재 정상본
- `save_slot_N.json.bak`: 직전 정상본
- `save_slot_N.json.tmp`: 기록·검증 중인 후보
- `save_slot_N.json.corrupt`: 교체 전에 발견한 손상 본 파일

저장 순서:

1. 입력 데이터를 현재 스키마 JSON으로 직렬화한다.
2. 같은 폴더의 `.tmp`에 기록하고 파일 스트림을 디스크까지 Flush한다.
3. `.tmp`를 다시 읽어 Decode와 마이그레이션이 성공하는지 확인한다.
4. 기존 본 파일이 정상이면 `File.Replace`로 본 파일을 교체하고 이전 본 파일을 `.bak`으로 남긴다.
5. 기존 본 파일이 손상이면 `.corrupt`로 격리하고 `.bak`은 보존한 채 `.tmp`를 본 파일로 이동한다.
6. 본 파일이 없으면 같은 볼륨의 `.tmp`를 본 파일로 이동한다.

로드 순서:

1. 본 파일이 유효하면 사용한다.
2. 본 파일이 없거나 유효하지 않으면 백업을 사용하고 복구 사실을 보고한다.
3. 본 파일과 백업이 모두 없거나 유효하지 않으면, 강제 종료가 남긴 유효한 임시 파일을 사용한다.
4. 어느 후보도 유효하지 않으면 각 후보의 원인을 합쳐 실패로 보고한다.

로드는 자동으로 파일을 다시 쓰지 않는다. 복구본을 읽은 뒤 다음 정상 Save가 새 본 파일을 만든다.

### 파일 시스템 경계

`ISaveFileSystem`은 읽기, 내구성 기록, 교체, 이동, 삭제만 추상화한다.
실제 구현은 `System.IO`를 사용하고, 테스트는 같은 저장 알고리즘에 실패를 주입한다.
경로와 JSON 규칙은 파일 시스템 구현에 들어가지 않는다.

### `SaveManager`

- 기존 정적 API를 유지하는 호환 Facade다.
- 상세 결과가 필요한 코드에는 `TrySave`, `TryLoad`, `InspectSlot`을 제공한다.
- 저장 시각과 현재 스키마 설정, Unity Console 로그만 담당한다.
- 파일 알고리즘과 마이그레이션 규칙을 직접 구현하지 않는다.

### `SaveDiagnosticsWindow`

`Hub To Home > Save > Diagnostics`에서 수동으로 여는 Editor 전용 창이다.

- 수동 슬롯 0~2와 자동 슬롯 99의 본 파일·백업·임시 파일 상태
- 실제 로드 가능한 소스, 스키마 버전, 저장 시각, 복구 메시지
- 저장 폴더 열기
- 확인 대화상자를 거치는 슬롯 삭제와 전체 초기화

창을 여는 것과 새로 고침은 읽기 전용이다.

## 오류와 복구 정책

- null 데이터와 음수 슬롯은 저장하지 않는다.
- 현재 정상 본 파일이 있는 상태에서 임시 기록 또는 교체가 실패하면 본 파일을 유지한다.
- 손상 본 파일 때문에 정상 백업을 덮어쓰지 않는다.
- 미래 버전은 migration 대상으로 낮추지 않는다.
- `Delete`는 본 파일, 백업, 임시 파일, 손상 격리 파일을 함께 정리한다.
- Console 사용자 메시지는 슬롯과 복구 소스를 보여주고, 상세 예외는 개발 로그에 남긴다.

## 테스트 전략

### Migration

- 버전 필드가 없는 기존 JSON을 버전 0으로 인식하고 현재 버전으로 올린다.
- 누락된 컬렉션이 기본값으로 복구된다.
- 미래 버전은 명확한 오류로 거절된다.
- 시나리오 없는 적, Room, 인벤토리, 보상, Encounter Memory가 왕복 보존된다.

### Atomic storage

- 첫 저장은 본 파일을 만들고 임시 파일을 남기지 않는다.
- 두 번째 저장은 최신 본 파일과 직전 백업을 만든다.
- 본 파일 손상 시 백업을 읽는다.
- 첫 저장 중단 형태에서 유효한 임시 파일을 읽는다.
- 교체 실패를 주입해도 기존 본 파일이 유지된다.
- 손상 본 파일 뒤 정상 저장 시 기존 정상 백업을 보존한다.
- 삭제가 슬롯 관련 파일을 모두 제거한다.

### Regression

- 기존 Save compatibility, Overworld Enemy, Encounter Memory 테스트
- Core 저장 전용 테스트
- 전체 EditMode 테스트
- Project Content Validation과 first-party Prefab Missing Script 검사

## 영향 범위

- `SaveData`에 필드 하나를 추가하지만 기존 JSON은 버전 0으로 호환한다.
- 기존 저장 API와 슬롯 파일 이름은 유지한다.
- Scene, Prefab, ScriptableObject는 수정하지 않는다.
- 사용자가 수정 중인 `TestMap.unity`는 수정하거나 스테이징하지 않는다.

## 완료 기준

- 검증되지 않은 JSON이 본 파일을 대체하지 않는다.
- 본 파일이 손상되면 직전 정상 백업을 로드한다.
- 구버전과 미래 버전의 처리 결과가 구분된다.
- 시나리오 없는 적 상태를 포함한 현재 저장 도메인이 왕복 보존된다.
- 개발자가 코드 없이 슬롯 상태를 검사하고 명시적으로 초기화할 수 있다.
