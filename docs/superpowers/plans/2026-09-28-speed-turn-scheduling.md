# 속도 누적 턴 구현 계획

> 최종 상태 (2026-09-28): 같은 작업 공간에서 구현·검증 완료. 후속 사용자 요청에 따라 증기 가속 샘플은 삭제하고 현재 브랜치 `codex/gameplayEdit`에 커밋·푸시한다. 서브에이전트, Unity Play/강제 Refresh는 사용하지 않는다.

**Goal:** 속도가 행동 순서뿐 아니라 빈도에도 반영되는 순차 실행 전투.

**Architecture:** 순수 C# BattleSpeedTurnScheduler가 캐릭터별 남은 준비량을 보존한다. 다음 도착 시간은 remaining / max(1, SPD). 최소 시간을 전체 참가자에게 적용하고 선택된 1명만 준비량 1000을 다시 부여한다. 전투 연출/입력 시간은 계산에 포함하지 않는다. 예고는 같은 상태의 복사본으로만 계산한다.

**Tech Stack:** Unity 6 C#, 기존 Turn QTE service/host, NUnit 및 Unity 외부 순수 C# 검증.

## 결정

- 라운드 정렬 반복이나 속도별 난수 추첨 대신 결정적인 누적 준비량 방식을 사용.
- 동일 도착 시간은 최초 등록 순서. SPD 변화는 이미 쌓인 준비량을 유지하고 앞으로의 속도에 반영.
- 새 참가자는 준비량 1000에서 시작. 죽거나 후열로 빠진 캐릭터는 제거. 후열 합류 시 기존 적 준비량은 유지.
- 선제공격은 첫 아군 턴 1회만 준비 완료 상태로 당김. 전체 아군 추가 턴/전투 시간 초기화 없음.
- 상단 0번은 현재 행동자, 이후는 예측 순서. 아직 일어나지 않은 버프/사망 등은 예측하지 않음.
- 후속 수정: 기존 스탯 상태의 예정된 자연 만료는 미래 예고에서 미리 계산한다. 현재 행동의 남은 종료/미래 자기 턴 횟수만 읽고 실제 상태를 틱하지 않는다. 새로운 부여·해제·사망은 여전히 발생 후 갱신한다. 자세한 실패→수정 기록은 [가속/턴 큐 계획](2026-09-28-haste-turn-queue.md)의 만료 오류 항목을 따른다.
- AP/상태이상 지속시간은 기존 개인 턴 기준. 빠른 캐릭터의 AP 회복·상태 소모 빈도도 함께 빨라짐.
- 원작의 정확한 내부 공식은 확인하지 않았으므로 원작 공식 재현이라고 표현하지 않음.

## 후속 승인: 관찰 가능한 턴 동작 기준으로 정리

사용자는 원작 내부 공식의 완전 복제가 아니라, 속도에 따른 추가 턴과 가속 적용/해제 시 미래 순서를 다시 계산하는 동작을 기준으로 진행하는 데 동의했다. 현재 누적 계산과 기존 선제 규칙을 유지하며, 가속을 즉시 턴 지급으로 바꾸지 않는다. 샘플 증기 가속은 SPD +100% / AP 8 / 3턴을 유지한다. UI 배치·입력·공격 연출·기존 DB 수치는 변경하지 않는다.

- [x] `BattleSpeedTurnSchedulerTests.cs`: 실험실 13/12/11 대 25에서 자기 가속 2배 전후 예고, 소비 없이 적용/해제 복구, 가속으로 쌓인 진행량 보존, 작은 가속에 순위가 같을 수 있는 사례를 고정한다.
- [x] `BattleTurnQteModuleControllerServiceTests.cs`: 자기 턴 가속과 만료를 실제 서비스 호출로 연결하고 현재 턴 유지/직후 실행과 예고 일치, 모듈 종료·재진입 후 변경 SPD 반영을 확인하는 검사를 추가한다.
- [x] 실제 계산기+NUnit 소스를 링크한 ignored `Temp/SpeedTurnChecks` CLI 실행기로 순수 검사만 실행한다. Unity 의존 검사는 기존 Editor 프로젝트 빌드로 컴파일까지만 확인한다.
- [x] 확인된 실패가 있을 때만 해당 런타임 경로를 최소 수정한다. 정상인 계산을 다른 임의 수식으로 교체하지 않는다.
- [x] 기존 인수인계/당일 기록/색인에 승인된 기준, 이번 변경 파일, 검증 범위와 남은 화면 확인을 기록한다.

결과: 순수 검사 15개 통과, 연결 검사 2개 추가·컴파일 성공, Editor 빌드 오류 0/기존 경고 2. 계산 실패가 발견되지 않아 이번 후속에서는 런타임 수식은 변경하지 않았다. 사용자 Unity Play 확인은 미실행 상태로 남긴다.
