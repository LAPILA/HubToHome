# 자료구조 알고리즘과 패턴 도감

[학습 홈](README.md) · [전체 코드 색인](20-code-atlas.md)

이름을 암기하기보다 **필요한 연산 → 자료구조 → 비용 → 실패 조건** 순서로 공부합니다. 아래 내용은 현재 코드에 있는 구현과 그에 대한 분석입니다. 복잡도는 코드 구조의 추정이며 측정된 성능 수치가 아닙니다.

## 자료구조 지도

| 구조 | 실제 사용 | 이유 | 주의점 |
| --- | --- | --- | --- |
| List | 턴 참가자, 명령 이력, 블록 자식 | 소수 원소 순회·순서 유지 | 탐색 O(N), 중간 제거 O(N) |
| Dictionary | 블록 상태, 풀 소유자, 피해 묶음 | 키로 빠른 조회 | 평균 O(1), 잘못된 키 설계가 더 큰 문제 |
| HashSet | 풀 중복 반환, 그래프 중복 보고 | 포함 여부·중복 방지 | 참조 동일성과 값 동일성 구분 |
| Stack | UIManager의 열린 창 | 마지막 창부터 닫기 | 중간 파괴·중복 등록 정리 필요 |
| Queue | 재사용 가능한 풀 객체 | 순서대로 꺼내기 | 이미 파괴된 Unity 객체 건너뛰기 |
| 고정 배열 | 상태 5종, 피해 타입 6종, 최근 타깃 4개 | 크기 명확·인덱스 접근 | enum/배열 크기 변경을 함께 관리 |
| 복사본 목록 | 턴 예고 | 실제 상태 변경 없이 시뮬레이션 | 내부 참조의 상태까지 바꾸지 않기 |

## 알고리즘별 읽기

### 이산 이벤트 스케줄링

BattleSpeedTurnScheduler: 가장 가까운 도착 시간만큼 전진합니다. 메뉴·애니메이션의 실제 시간과 분리됩니다. 한 선택 O(N), K개 예고 O(NK), 동기화는 참조 탐색으로 O(N²). 소수 참가자에서는 구현 단순성이 중요합니다.

### 가중 랜덤과 순환 버퍼

BattleEnemyTargetSelector: 최근 네 칸에 타깃 참조를 기록하고 가중치를 줄입니다. 기록은 `(index + 1) % length`로 돌아갑니다. 최근 길이 4가 고정이면 후보 수에 대해 O(N)입니다. 매번 완전 균등 랜덤보다 연속 집중을 완화하되 순번 공격처럼 예측 가능하지 않게 합니다.

### DFS 순환 검출

SequenceCallGraphValidator: 노드는 Sequence ID, 간선은 sequence.call입니다. 방문 전/방문 중/방문 완료 상태를 구분합니다. 기본 그래프 순회는 O(V+E), 보고할 순환 경로 문자열을 복사하는 추가 비용은 별도입니다. 깊은 재귀의 최대 깊이도 생각해야 합니다.

### 탐욕 줄바꿈과 이진 탐색

SmartTextWrapper: 지금 줄에 들어가면 붙이고 넘으면 줄을 바꿉니다. 너무 긴 단어의 조각 길이는 이진 탐색합니다. 폰트 폭 측정·문자열 생성까지 포함해 비용을 설명해야 합니다.

### 상태 스냅샷과 복구

SaveDataCodec, SequenceRecoveryStore: 현재 상태를 복사해 독립적인 기록으로 다룹니다. 스냅샷은 디자인 패턴 이름보다 **복사 깊이와 복원 범위**가 중요합니다. 게임 진행도 저장과 에디터 미저장 편집 복구는 다른 수명입니다.

## 패턴 판정표

| 패턴 | 확인된 사례 | 과장하면 안 되는 주장 |
| --- | --- | --- |
| Adapter | IActionAdapter 구현, GlobalDataShopTransactionStore | interface가 있다고 모두 Adapter는 아님 |
| Command | SequenceEditCommandStack + ISequenceEditCommand | 모든 런타임 Action이 Undo 가능한 것은 아님 |
| Observer | Changed 및 전투 이벤트 구독 | 이벤트만 쓰면 결합이 사라지는 것은 아님 |
| Factory | StatusEffectFactory | 모든 static 함수가 Factory는 아님 |
| Object Pool | ObjectPoolManager | 풀을 쓰면 무조건 빠르거나 할당 0은 아님 |
| State Machine | 전투·여행·게임 상태 전환 | 상태 enum만 있다는 것과 올바른 전이 보장은 다름 |
| 범위 기반 정리 | 카메라 ActionScope, 오디오 억제 범위 | C# Dispose가 모든 강제 중단에서 자동 실행되는 것은 아님 |
| 데이터 주도 구성 | SkillData + 블록, Scenario Catalog | 데이터로 만들면 검증 비용이 사라지는 것은 아님 |
| Facade | SaveManager | 큰 Manager에 모든 로직을 넣으라는 뜻이 아님 |

프로젝트 전체를 MVC·ECS·클린 아키텍처로 단정하지 않습니다. 부분적으로 사용한 구조와 전체 아키텍처는 다릅니다.

## C# 개념을 실제 코드에 연결

- **제네릭**: BattleSpeedTurnScheduler<T>는 Unity 객체를 몰라도 스케줄을 계산할 수 있습니다.
- **delegate / Func**: 속도·우선순위·글자 폭을 함수로 받아 테스트 입력을 바꿉니다.
- **readonly struct**: 결과·요청의 필드 재할당을 제한합니다. 내부 참조 객체까지 깊게 불변은 아닙니다.
- **IEnumerator**: 프레임 간 진행 상태를 보존합니다. 일반적으로 메인 스레드에서 동작합니다.
- **partial**: CameraController·ShopUI의 파일 분리입니다. 별도 객체로 책임이 분리된 것과 같지는 않습니다.
- **Unity null**: 관리 참조는 남아 있지만 native 객체가 파괴될 수 있습니다. ReferenceEquals와 Unity == null은 의미가 다릅니다.

## 실습 과제

1. Unity 없는 작은 C# 프로그램으로 두 배우의 다음 10턴을 계산합니다.
2. 타깃 표본값을 0, 0.5, 1로 고정해 어떤 인덱스를 고르는지 추적합니다.
3. A→B→C→A와 A→B, A→C→B를 각각 그래프로 검사합니다.
4. 상태를 List에 얕게 복사한 버전과 원소까지 복사한 버전의 차이를 출력합니다.
5. 풀 객체를 중복 반환했을 때 HashSet을 제거하면 무엇이 깨지는지 작은 모형으로 재현합니다.

기존 프로젝트 데이터를 망가뜨리는 실습보다 작은 콘솔 모형과 임시 테스트를 권합니다.
