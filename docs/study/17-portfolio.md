# 포트폴리오 사례와 면접 설명 연습

[학습 홈](README.md) · [전체 코드 색인](20-code-atlas.md)

포트폴리오는 기능을 많이 나열하는 문서가 아니라 **문제를 정의하고 구조를 선택한 이유를 검증 근거와 함께 설명하는 문서**입니다. 이 프로젝트는 AI 보조 개발이므로 실제 본인 기여와 이해 수준을 분명히 구분합니다.

## 먼저 채워야 할 기여 기록

| 질문 | 본인이 작성할 내용 |
| --- | --- |
| 내가 결정한 요구사항은 무엇인가 | 실제 결정과 근거 |
| 내가 직접 작성·수정한 코드는 어디인가 | 파일·메서드·커밋 또는 작업 기록 |
| AI가 작성한 부분은 무엇인가 | 생성 범위와 검토 방식 |
| 내가 직접 재현한 실패는 무엇인가 | 재현 조건·영상·로그 |
| 내가 보증할 수 있는 검증 범위는 어디까지인가 | 엔진 실행·기기·자동 검사 구분 |
| 다시 구현해 볼 수 있는 핵심은 무엇인가 | AI 없이 설명·재작성한 작은 예제 |

“기획부터 엔진까지 혼자 전부 구현했다”처럼 확인되지 않은 기여를 쓰지 않습니다. 반대로 AI 사용 사실만 적고 끝낼 필요도 없습니다. 실제로 확인한 설계 판단·오류 분석·검증 결과를 보여 주면 됩니다.

## 사례 A 턴 예측과 실제 실행의 일치

**문제**: 임시 속도 효과가 끝나면 상단의 연속 턴 예고가 실제 진행과 달라질 수 있습니다.

**구조**: 남은 준비량을 가진 이산 스케줄러로 실행하고, 같은 함수를 복사본에 적용해 예고합니다. 가상 행동 완료 횟수로 기존 버프 만료를 예측합니다.

**핵심 판단**: UI를 위한 예고가 실제 상태를 변경하지 않게 합니다. 미래의 알려진 만료는 반영하지만, 아직 선택하지 않은 새로운 스킬·사망까지 예측한다고 약속하지 않습니다.

**코드**: BattleSpeedTurnScheduler, BattleTurnQueueProjection, CharacterBase.GetForecastSpeed.

**면접 질문**: 왜 우선순위 큐가 아닌 List인가? 동률은 어떻게 안정화하는가? 버프 해제가 갑자기 발생하면 예고는 언제 바뀌는가?

**보강할 증거**: 동일 시드·동일 상태에서 예고 suffix와 실제 턴 결과 비교, UI 캡처, 실제 테스트 실행 기록.

## 사례 B 안전한 저장과 복구

**문제**: 저장 실패가 정상 파일을 손상시키거나, 스냅샷 정규화가 현재 파티를 바꾸면 안 됩니다.

**구조**: SaveManager 정책 → 복사본 → Codec → 검증된 임시 파일 → 원자 교체·백업. 미래 버전 거절과 복구 후보 탐색을 분리합니다.

**핵심 판단**: 포맷과 파일 시스템을 분리해 고장 주입이 가능하게 합니다. 자동 저장은 요청 즉시가 아니라 안전한 탐색 상태에서 확정합니다.

**기록된 검증**: 2026-10-11 관리형 155/155는 설정·저장·장비 관련 하네스 전체 결과입니다. 저장만의 155개 Unity 통합 테스트가 아닙니다.

**면접 질문**: 얕은 복사로 충분한가? File.Replace 실패 시 어떤 파일이 남는가? 자동 저장 요청 후 새 게임이면 어떻게 되는가? 콘솔 저장 API 차이는 어디서 격리할 것인가?

## 사례 C 제작자의 작업을 보존하는 Sequence Maker

**문제**: 여러 편집 창, 외부 YAML 변경, 미저장 Runtime Asset, 도메인 리로드가 작업을 잃게 할 수 있습니다.

**구조**: 공식 편집 창 하나, 문서별 명령 이력, 상태 ID 기반 dirty, 명시적 검증 저장, 외부 변경 충돌, Library 복구본.

**핵심 판단**: UI Toolkit/Odin 사용 자체보다 저장·실행·문서 상태를 분리한 것이 중요합니다. 안정적인 BlockId로 순서 변경에도 참조를 유지합니다.

**코드**: SequenceMakerDocumentSession, SequenceEditCommandStack, SequenceSaveCoordinator, SequenceRecoveryStore.

**면접 질문**: Undo를 한 뒤 다른 명령을 넣으면 왜 dirty가 단순 개수 비교로 안 되는가? 복구본을 Assets 밖에 두는 이유는? 편집기가 BattleManager를 직접 찾지 않는 이유는?

**보강할 증거**: 실제 편집→Undo→외부 수정 충돌→복구 시연. 과거 설계 화면이 현재 구현 화면과 같은지 확인하고 캡처합니다.

## 사례 D 표현의 수명과 전투 규칙 분리

**문제**: 연타 피해 숫자 겹침, 파괴된 UI Tween, 옛 카메라 연출의 늦은 복구가 전투 가독성과 안정성을 떨어뜨립니다.

**구조**: 대상+행동 묶음+피해 타입으로 숫자 집계, View별 Tween 소유권, 카메라 최신 토큰 검사, 풀 객체 반환 시 초기화.

**핵심 판단**: 화면을 보기 좋게 하려고 HP 계산을 합치지 않습니다. 전체 DOTween을 강제 종료해 다른 연출을 끊지도 않습니다.

**면접 질문**: 같은 DB를 공유한 위젤 세 명은 어떤 키로 구분하는가? 새 카메라 연출을 옛 Dispose가 덮어쓰지 못하게 하는 방법은? 풀링의 단점은?

## 사례 E 읽기 전용 콘텐츠 검사

**문제**: ID·참조·카탈로그 오류는 런타임까지 가서 발견하면 원인을 찾기 어렵습니다.

**구조**: 자산 수집 → Snapshot → 독립 검사 규칙 → 오류 코드·심각도·대상 → 제작 도구에서 이동. 실제 수정 명령은 별도입니다.

**면접 질문**: 왜 검사와 자동 수정을 분리했는가? 오류 메시지가 아니라 안정적인 코드가 필요한 이유는? 검사 규칙을 엔진 없이 어디까지 시험할 수 있는가?

## 발표 구성

1. 30초: 어떤 게임이고 내가 해결한 기술 문제는 무엇인가.
2. 2분: 한 사례의 실패 장면과 재현 조건.
3. 3분: 구조·데이터 흐름·대안 비교.
4. 2분: 검증과 아직 남은 한계.
5. 30초: 이후 개선 방향과 직접 배운 점.

파일 수, 코드 줄 수, “완벽”, “모든 기기 최적화 완료”를 성과의 대체 지표로 쓰지 않습니다. 저사양 모바일·Switch 성능은 실제 기기 프로파일 기록이 있어야 주장할 수 있습니다.
